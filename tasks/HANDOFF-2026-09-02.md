## 2. THE ONE THAT EXPLAINS THE OTHERS — "still loading" rendered as an answer

He sent two screenshots of the same PO drill-down seconds apart: the first
tagged every line **STOCK**, the second showed **HC-SO-001162 · PENDING**.

**STOCK is not a blank.** It is a claim — "no open Sales Order demand is
assigned to this line" — so while a second query was in flight the screen
asserted that goods bought for a named customer were unassigned stock.

A drill-down runs TWO queries (the lines, and the coverage saying which order
each line was bought for) and gated on the FIRST only, then read the second as
`x ?? []`. **"I do not know yet" collapsed into "I know, and the answer is
none."** Four of the eight drill-downs did this; four run one query and were
already correct.

**This also closed the Incoming PO question he raised twice.** `0596` fixed the
missing FETCH; the loading window survived it, which is why the column still
looked blank.

The fix is three states, never two — `ready` / `loading` / `unavailable` — with
`coverage` a **REQUIRED prop**, which is what enumerated the call sites: the
compiler named all seven. Full rule in `docs/modules/coverage-state.md`.

**Not audited, and the obvious next gap:** `MobileModuleDetail.tsx` and
`MobileRelationshipMap.tsx` also call `usePoSoCoverage` and render their own
cells. They were not changed.

## 3. ARRIVAL AND SHIPPING ARE NOW TWO COLUMNS

Offered three shapes; he chose two columns. Stock Status keeps answering
ARRIVAL; the new **Delivered** column answers SHIPPING as `2 / 5`.

The figures were never missing — both surfaces already summed them from the same
deliverable engine the picker uses, and only the `none|partial|full` verdict was
emitted. **No new read.**

Three shapes are refused rather than guessed: a missing figure is `unknown`
(never zero), nothing-to-ship is `none` (never `full`), and an over-delivery
keeps both numbers (`6 / 5`).

**Naming trap, pinned by a test:** `delivery_state` is ALREADY two different
things — the stored scheduling override on `mfg_sales_orders`
(`PENDING_SCHEDULE`) and the computed shipping verdict that SHADOWS it on the
detail response — and two exported types are both called `DeliveryState`. The
new fields deliberately avoid that prefix.

## 4. THE SLOWNESS — measured, and three suspects that look identical

*Client errors dump (read-only)*, 3-day window, occurrences:

| endpoint | slow occurrences |
| --- | --- |
| `/api/presence` | 354 |
| `/api/announcements/banner` | 343 |
| everything else | 64 |

**`GET /api/auth/me` does not appear at all**, and `system-health.md` names it as
the clean proof the DB auth path is being paid. That is the closest thing to
evidence the pass-renewal fix worked — but **NOT proof**: the dump groups by
signature with a last-seen date, so it cannot be split around the 2026-08-31
18:41 UTC deploy. Recorded LIKELY.

Every 60s each visible tab does three things on one connection and the log
records only the third, so all three read as "presence is slow":

* **B — the authorization gate**, two joined reads when no valid pass.
* **C — the heartbeat WRITE** (`POST /presence/heartbeat` runs
  `UPDATE users SET last_seen_at`), **uncached by construction**; the edge cache
  only covers the GET after it.
* **A — the TTL**: presence keeps its copy **15s** while the browser asks every
  **60s**, so a lone user misses every poll. The banner note records the same
  shape measured at 874-984ms before ITS TTL was raised; presence never was.

**Nothing was changed on a hypothesis.** #2867 ships the probe:
`/api/admin/health/live` gains `authFastPath`, a second System Health card
reporting what the request in hand DID (`pass` / `session-db` / `unknown`)
beside each cache TTL and the browser poll.

**OWNER ACTION OWED: open System Health once and read the new card.** `pass`
means chase A and C. `session-db` means chase the pass, not the caches.

Why the direct check was impossible here: `wrangler secret list` fails from this
machine — `backend/wrangler.toml`'s `account_id` is not one this login owns.
