## 2. THE VENUE — fixed, repaired, and one surprise

**What happened.** Opening a mirrored 2990 order and saving it blanked the venue,
permanently. The audit log for `2990-SO-2608-070` records `venue: "2990s PJ" ->
""` and `venueId: null -> "5cafa0a2…"` in ONE save at 07:50:31.

**Why.** The desktop default-venue effect guards the venue ID but not the NAME
(`?? ''`), and `if (form.venueId) return` makes the effect a one-shot — so the
blank it writes can never be repaired by a later pass. Every mirrored 2990 order
starts in exactly that state, because the mirror forces `venue_id: null` while
keeping the text.

**Fixed in three layers**, because the client one stops it being sent and the
server one stops it whatever sends it:

* the effect returns instead of writing an unresolved name (desktop + consignment);
* `venueNameForHalfWrittenPair` in `scm/lib/venue-binding.ts` — a blank `venue`
  beside a real `venueId` is a half-written pair, not a clear. **Three answers,
  and the third is load-bearing:** `unresolved` (the master could not be read, or
  the id names nothing) makes the route DROP the venue from the patch rather than
  write the blank, so a database blip cannot delete a venue;
* clearing a venue is still allowed and still easy — send BOTH empty.

**Repaired.** `repair-blanked-venue`, MODE=apply, company 2, run 33424502242:
**5 orders got their venue back.** All five now read "2990s PJ".

### The surprise, and it is worth knowing before the next repair

That run printed **VERIFY FAILED** on all five rows it had written correctly.

`0229_venue_canonicalize.sql` puts `trg_mfg_sales_orders_canonicalize_venue` on
the table — BEFORE INSERT OR UPDATE OF venue — which folds known aliases, because
the same showroom kept re-appearing as both "PJ Showroom" and "2990s PJ" and
three one-shot cleanups each drifted back. **Canonical is "2990s PJ".** The
repair sent the master's spelling, the trigger stored the canonical one, and the
verify compared against the value it had SENT.

A verify that fails a GOOD write is the more dangerous direction: a red line in a
log invites the next person to re-run or revert a repair that worked. Fixed in
#2839; ledger `docs/bugs/0594-*`. The general rule now written into the module
guide: **before writing a verification, ask what the database does to a value
between the write and the read.**

Still open, reported and deliberately not done: the `scm.venues` master row still
carries the alias spelling, so the PICKER hands out "PJ Showroom". Folding it is
`backfill-canonicalize-venue.mjs` (dry-run gated). **Never run — do not claim
what it would do.**

## 3. THE SLOW PAGES — measured, and the root cause is NOT what the first entry said

**What he saw.** Repeated one-second `GET /api/presence` and `GET /api/branding`
on a Sales Order page.

**It is not one page or one person.** Client-error log, 2 days, run 33419722133:
50 signatures / 444 occurrences, **45 of the 50 `[slow …]`**, on endpoints that
are already edge-cached:

```
     20 [slow 800ms+] GET /api/announcements/banner
     14 [slow 800ms+] GET /api/presence
      3 [slow 800ms+] GET /api/branding
      2 [slow 800ms+] GET /api/auth/me
      1 [slow 5s+]    GET /api/presence
```

`GET /api/auth/me` is the decisive row — it returns the authenticated user and
nothing else, so it has no route body to blame, and no route cache helps because
the cache lives INSIDE the handler.

**Root cause — two constants with nothing between them:**

| | value | where |
|---|---|---|
| signed pass | **8 hours** | `SESSION_PASS_TTL_MS` |
| session token | **7 days** | `SESSION_TTL_SECONDS` |

A pass is minted at exactly four places — `/bootstrap`, `/login`, `/totp/login`,
`/accept-invite` — and **nowhere else**. No renewal. So from hour 9 to day 7,
about **95% of a session's life**, every request ran `getUserBySession`: a
six-table join plus a four-branch `UNION ALL` on the shared pool, before any
route body. In plain terms: fast for the first 8 hours after a login, slow for
the six days after it, unless somebody logs out and back in.

Fixed in **#2838** — the middleware re-issues on the authoritative path (reaching
it *means* the caller has no usable pass) and returns it on `X-Session-Pass`; the
SPA absorbs it in `correlatedFetch`, the one funnel every authenticated transport
uses. Safe because the revocation board already anticipated re-issue: it compares
a pass's `iat` to the revoke stamp.

### A correction, recorded rather than quietly fixed

`docs/bugs/0592-*` and its module-guide section state that this slowness is
`SESSION_SIGNING_KEY` being **unset**. **That was a claim with no observation
behind it** — the state of that secret was, and at the time of writing still is,
unreadable from inside this repository, which is exactly why #2836 added the
panel. Both documents are corrected. The renewal gap is present and costly either
way, which is what makes it the root cause rather than a second theory.

**Deployed and half-verified.** Deploy run 33426836520 — run `success`,
`backend` `success`, `frontend` `success`. Both ends of the renewal are confirmed
on the live site: the shipped bundle carries `absorbSessionPass`
(`/assets3/initial-app-Chx9Iyq8.js`), and the worker answers
`Access-Control-Expose-Headers: X-Request-Id,X-Company-Code,X-Session-Pass`, so
the browser is allowed to read the renewal.

**What is NOT yet measured: whether it is faster.** The evidence lives in the
client-error log, whose window is DAYS, so re-running it today would mostly
re-read pre-deploy data. Measure a day later with **Client errors check
(read-only)** and compare the `[slow …]` counts on `/api/auth/me`,
`/api/presence` and `/api/announcements/banner` against the block above. Read
System Health's **Signed sessions** card at the same time.

### Ruled out, so nobody re-chases it

No `server-error` signature appeared in two days, and `api/client.ts` reports
every API 5xx including 504. **The 504 in his capture was not an API call made
through the app** — it was the page document, which Cloudflare serves before any
of this code runs.

## 4. PURCHASE ORDERS WERE MISSING WHAT THE SALES ORDER ALREADY KNEW

**Found by re-measuring rather than trusting the plan.** The sofa/bedframe
completeness audit (run 33421554052) showed the PO side of BEDFRAME far behind
its own SO side — colour **30.8%**, dimensions **32.5%**, against 97.7% and 98.1%
on the sales side. Sofa's two sides tracked each other, so it was never a sofa
problem.

The audit could not say what to do about it, so #2837 taught it to split the
answer two ways. Run 33421968564:

```
  line-level: total 745 / aligned 420 / disagree 325
     by SHAPE — PO missing what the SO holds: 322 / SO missing: 1 / CONFLICT: 2
     of the PO-missing lines, the value IS in the PO's own AutoCount remark
       (a decoder miss, ours to repair): 285;
       the book's purchase line never said it (his call, not a repair): 37
     by PROVENANCE — bedframe: 322 imported, 0 raised in the ERP
     (of ALL 745 dedicated lines: 745 imported, 0 raised here)
```

That is what made the repair safe to run: **285 of the values were written in the
purchase line's own AutoCount remark and the decoder had not read them**, so
recovering them is a COPY of what the book says — the owner's migration rule is
satisfied. The other 37 are not ours: the book's purchase line never carried the
value, and putting the sales order's value there is a decision about what the
supplier is told to build.

**Applied**, after adding a fills-vs-changes report so the risk was visible first:

```
DRY-RUN: 2855 would FILL a blank; 0 would CHANGE a value that is already there
APPLY  : merged 471 of 471 bedframe lines (RETURNING)
         READ-BACK on a NEW connection: 471/471 merged rows hold a jsonb OBJECT
```

Re-measured by the audit itself afterwards (run 33422759912 — the independent
instrument, not the writer's own report):

| PO bedframe axis | before | after |
|---|---|---|
| dimensions (divan / leg / gap) | 32.5% | **98.5%** |
| colour | 30.8% | **98.9%** |

**325 disagreements down to 5**, and none of the five is ours to fix by copying.

### What this does NOT say

**All 745 dedicated PO lines are imported; ZERO were raised in the ERP.** So this
data cannot tell you whether `POST /mfg-purchase-orders` drops the SO's variants
today — it reads `it.variants` off the request body and never consults the source
SO line. That is UNMEASURED, not cleared, and it is the thing to watch the first
time a purchase order is raised here from a sales order.

## Four things stated wrongly, and how each was caught

None was caught by the owner. Each was caught by two of my own numbers
disagreeing — which is the only reason to write them down.

1. **"Delivering goods never moves the sales order's status."** False. It has for
   months (`lib/so-delivery-sync.ts`). I grepped `routes/delivery-orders-mfg.ts`
   for `.update(` on the SO table, found none, and answered a question about the
   SYSTEM with evidence about one FILE. The update lives in the module that file
   calls.
2. **"480 photos are missing."** No. The importer attaches ONE photo per sofa
   BUILD, on the first compartment piece — the owner's own 2026-08-10 ruling. I
   counted per LINE. Its own resolve pass says `602 planned (already attached:
   602)` and `238 / 238`. Nothing attachable is unattached.
3. **"Sofa photos are deliberately held for the sofa round."** No — that is a
   stale header comment. `sofa held: 1121` means the ERP has no line for that
   AutoCount doc+model, i.e. the order was never imported.
4. **"The repair ran and nothing needed fixing."** The repair ran over 68 orders,
   changed nothing, and exited 0 — because `pgrest-shim` cannot execute the
   embedded select the sync reads coverage with, and the sync swallows a throw
   per document. `docs/bugs/0599-*`.

## Two guards written into code, not into advice

* `resync-so-delivered-status.mjs` PRE-FLIGHTS its coverage read and `exit 3`s
  when it cannot execute. A repair that cannot do its work must say so.
* Its PLAN names every document it would move. The earlier version printed "this
  plan cannot predict its verdict" — a plan that cannot say what it will do is
  not a plan, and it is what let the silent no-op through.
