
Confirmed against the live staging API afterwards: 113 of 113 BEDFRAME and 187

**Do not re-run the clear.** The full account is `docs/option-pool-clear-coe.md`
and `docs/bugs/0855-...`. The short version: for MATTRESS and BEDFRAME,
`allowed_options.sizes` is not a restriction, it is the record of which sizes a
Model comes in — `product-models.ts` PATCH `/:id` says so ("the SINGLE source of
truth for ON/OFF"), and the Modular screen says so to the user's face ("only
ticked variants surface when you 'Add codes' or when the SO/PO line picker offers
a variant"). Mattress thickness has no other home at all.

### The decision this leaves open, framed properly

The owner's original problem is real: a Model's pool stopped him picking a fabric
colour that exists. The same column holds two different things —

| shape | keys | clearing it |
|---|---|---|
| **restriction** — "do not offer this for this Model" | `fabrics`, `specials` | opens the picker, safe |
| **configuration** — "this Model comes in these" | `sizes` (MATTRESS/BEDFRAME), `mattress_thickness_cm` | DELETES data |

Three options, recommendation first:

1. **Clear only the restriction-shaped keys.** Solves the reported problem,
   leaves configuration alone. **Recommended.**
2. **Split the column** so the two stop sharing a home. Correct long-term; needs
   a migration and touches the Modular editor, the SKU generator and the POS
   catalogue read.
3. **Leave it as restored** and handle each unwanted restriction as it appears.

## 2. What the picker/save audit found (the owner asked for this directly)

> 「我们的 SO dropdown/picker 是不是从这里的开放来选，然后不要 save 不到，不要
> 2990s 那些突然有 bugs 选不到啊」

**Can a dropdown go EMPTY when a pool is cleared? No.** Both picker filters read:

```ts
if (!Array.isArray(pool) || pool.length === 0) return [...opts];
```

An empty pool returns the FULL master list, which is the same reading the save
gate takes (`hasRestriction` = a non-empty array). Clearing a pool opens a
picker; it cannot empty one. What DID go empty is the **Modular editor**, which
renders its ticked boxes from the pool, and **"Add codes"**, which generates SKUs
from it.

**Can something be offered and then refused on save? Not today, and it is now
pinned.** Both sides normalise identically — `normaliseTypographicQuotes(s).trim()`
— which is the fix from `docs/bugs/0814` (79 sofa Models carry the fabric
`"TARONI "` with a trailing space; before the fold the screen offered it and the
save refused it).

That agreement was held by **two hand-copied implementations under different
names**, which `check-shared-mirrors.mjs` cannot compare — its own header says a
rule re-implemented under another name is invisible to it. It is now pinned by
`frontend/src/vendor/shared/pickerAgreesWithSaveGate.test.ts`, 11 cases: empty
pool opens, non-empty restricts, an already-chosen value stays editable, trailing
space and both curly inch marks match, and case is NOT folded (widening it would
merge two real inventory buckets, since these strings compose `variant_key`).
