## An ancestor in the account book can still be the wrong version of itself, and the cascade walked straight past it [high]

<!-- area: AutoCount sync + write-back -->

**白话.** 老板 2026-08-26:

> 「如果我 edit 了之后直接开 DO/SI,然后我的 edit 还没进到 AutoCount,我点 send now,
>  它也会把这个最新 version send 进去了,然后继续 update 到完,对吗?」

**不会。改完之后开的单,会照帐本里那个旧版本去转。**

**为什么.** Send Now 的补上游功能问的是「上游**在不在**帐本里」,一碰到在的就停:

```ts
if (parent.linkedAcDocNo) break;   // 在帐本里 —— 上面的一定也在
```

那句注解是对的:**「在不在」会往上传递** —— 一张单能进帐本,只能是靠它的上游进去的。

**但「新不新」不会往上传递。** 一张销售单可以既在帐本里、又不是你现在看到的那个版本。
转档就会把旧的行带进正式帐本,而**没有任何地方会讲**。

**而且旧的那张可以坐在新的上面** —— 发票的上游是送货单(是新的),送货单的上游是销售单
(开完送货单之后你又改过)。走到送货单就停,等于回报「没事要做」,然后拿旧订单开发票。

**修法.**

- 走到**链的顶端**,不再碰到第一张在帐本里的就停。链只有两阶,多读一两次而已。
- 每一层判两件事:
  - **不在帐本里** → `missing`,照旧补进去
  - **在帐本里,但队列里还压着没送出去的 edit** → `stale`,先把那笔 edit 送出去

**「旧」的定义是「有一笔没送出去的 edit」,不是「跟帐本比对有差」。** ERP 本来每次改单
就会排一笔 edit,所以**那笔 edit 还在队列里,本身就是「帐本落后了」这句话** —— 用我们
已经有的资料判断,不必多打一次主机,也不会对「什么叫不一样」有第二种意见。edit 全部送
完的单就算是最新的,这正是那个队列存在的意义。

**pending 和 failed 都算.** pending 是排水还没轮到,failed 是排水放弃了。**站在开单的
人那边,两个是同一件事:帐本没有我的修改。** 只处理一种,等于修好一半又讲不清楚。

**送的是那笔 edit,不是「最新的那一列」.** 一笔 create 的重送会比 edit 新,照「最新」
去挑就会重送 create、把修改丢在后面 —— 这正是测试钉死的那一条。

**两笔没送的 edit,先送旧的那笔.** 两次修改是有先后的,先送新的会把顺序做反。一次按钮
送一笔,下一次按钮送下一笔。

**顺序仍然是由外而内.** 上游是 `stale`、下游是 `missing` 的时候特别要紧:先转档再回头
更新订单,送货单就会带着订单已经没有的行。

**`ancestorsMissingFromBook` 直接删掉,不留.** 它回答的是同一个问题的旧版本,留着就是
一个规则两个家 —— repo 的 `audit:duplicated-decisions` 挡的正是这个。

**还没做的:画面不会告诉你它做了什么.** 后端会回 `ancestors_sent`(现在还带上
`missing` / `stale` 的原因),但前端一个字都没读。按下去补了三张单,操作的人看不到。
