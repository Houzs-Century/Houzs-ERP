## A public share link could lock out its own visitors: every valid request counted toward the brute-force limit [high]

**Symptom.** Owner, 2026-09-09 ~10:20 UTC: "CHECK YEN CREATIVE LINK CANNOT ACCESS", then "CURRENTLY ALL LINK CANNOT ACCESS" — every contractor calendar link showed "Could not load the schedule just now" from the office, minutes after a Band of Gorilla export from the same links had worked (09:05).

**Root cause (traced).** The public share routes ran `checkRateLimit(c, "<kind>_share_read", clientIp(c), 300, 900)` BEFORE resolving the token, so every request from one address counted toward the cap — a page load, the 60-second live poll of every open tab, each event tap (two more calls), each export. Past 300 in 15 minutes, `rateLimit.ts` answered 429 to every request from that address, and the page's non-404 branch rendered the generic "Could not load" text, so the lockout looked like an outage. Observed rather than inferred: the database side was read on production (tokens present and unrevoked; the schedule query returns 16 rows for YEN CREATIVE; no postgres errors since 09:20), `git diff 6d9df710..origin/main` showed no change behind the public routes since the working export, and the new read-only workflow **Probe share links** (run 34342181682, 10:49 UTC, from GitHub's network) got HTTP 200 with events from all five active links while the office still could not load them — so the answer depended on WHO was asking, which is the limiter's signature. What stays UNKNOWN: whether the backend sees the office's real address or one address shared by every visitor of `erp.houzscentury.com` (the site forwards `/api/*` to the Worker through `frontend/functions/api/[[path]].ts`, a `fetch(upstream, request)` hop); either way a valid token is not a guess and must not count.

**Fix.** `rateLimit.ts` gains `rateLimitExceeded` (read-only check) and `bumpRateLimit` (increment). Both public gates ask the check first, resolve the token, and bump ONLY when the token is unknown or revoked — a guesser still pays per wrong link and is still refused at the cap; a visitor with a valid link never counts. The page now names a 429 instead of the generic text. Pinned in `backend/tests/publicShareRateLimit.test.ts` through the real routers with a fake KV: five valid loads leave the counter at 0 (RED on the unfixed tree: counter was 5), a wrong link is 404 and counts, and a counter at the cap makes even a valid link 429. The probe workflow stays as the instrument for next time.
