## A parenthesised sofa code was unfindable by its full code [high]

<!-- area: Sales orders + pricing -->

**白话.** 搜寻栏把 `,(){}` 这几个字元**直接删掉**。删在字串**结尾**没事，删在**中间**就完蛋 ——
`2376-1A(RHF)` 被送成 `%2376-1ARHF%`，一笔都对不上。而 `(LHF)` / `(RHF)` 正是这个
型录用来分左右手沙发的写法，所以**每一个带括号的沙发料号，在每一个有搜寻的清单里都
找不到**。

- **发现:** 2026-08-22，在 prod（Houzs Century，Products 清单）实测
- **状态:** 已修

### 现场重现

| 搜寻字串 | 实际送出的 pattern | 找到几笔 |
|---|---|---|
| `2376-1A` | `%2376-1A%` | 6 |
| `2376-1A(` | `%2376-1A%` | 6 ← 括号在结尾，删掉刚好没事 |
| **`2376-1A(RHF)`** | **`%2376-1ARHF%`** | **0** ← 这个料号是存在的 |

前端送出去的字串是完整的（`?search=2376-1A%28RHF%29`），坏在后端。

### 原本为什么会这样写

`postgrest-search.ts` 的用意是对的：PostgREST 的 `.or()` 语法用 `,` 分隔条件、用 `()`
分组，所以搜寻字串里的这些字元会**破坏过滤语法**（PostgREST 不是回 400 就是回错的
资料）。

错的是补救方式，还有它给自己的理由：

> 「`ilike` 还是会透过前后的 `%...%` 万用字元match」

这句**只有在被删的字元在字串两端时才成立**。从中间删掉一个字元，这个字串就不再是原
值的子字串了。而这个档案的注解从一开始就写着 `BOOQIT-1A(LHF)` 当例子 —— **它举的例
子正好是它治不好的那一种**。

### 修法

每个保留字元改成 **`_`**（LIKE 的单字元万用字元），不是删掉。位置和长度都保住，所以
`%2376-1A_RHF_%` 对得上 `2376-1A(RHF)`。

**取舍讲清楚：** `_` 会match任何一个字元，所以字串稍微松了一点 —— 同长度、只有那几个
位置不一样的字串也会被match到。这是一个**有界的放宽**，对上的是**今天保证零结果**。

而且它跟这个 codebase 本来的规则一致：操作人员打的 `%` 和 `_` 本来就当万用字元送出
去。所以「一个送不出去的字元变成单字元万用字元」是既有规则，不是新规则。

### 没有在这支做的

真正精确的修法是 PostgREST 的**双引号值**（`code.ilike."%2376-1A(RHF)%"`，引号内
`,()` 是字面值）。

但引号必须包住**整个** pattern（含 `%`），而 **43 个呼叫点**都是自己组 `%${s}%` 的
—— 那是横跨 15 个档案的机械性改动，不是这个档案里的一行。

值得做，但不值得跟「让搜寻不要回零笔」这个修复绑在一起。
