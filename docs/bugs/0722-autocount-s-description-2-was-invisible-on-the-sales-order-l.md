## RETRACTED — AutoCount's Description 2 was already carried into the remark; this entry's fix was a duplicate that would have doubled the text [high]

**This entry is a RETRACTION of its own first version.** The first version
claimed the book's Description 2 had never been carried into the sales-order
line remark, and shipped a second tool to do it. Both halves were wrong. The
tool was merged in #3292 and is REMOVED by the PR carrying this rewrite, before
it was ever applied to production.

**What the owner asked.** 2026-09-08: 「记得把autocount的这个description2 remain
着搬进去我们的remark」. He had asked the same thing on 2026-09-02 —「那个
description 2 也要记录进我们的 remarks 里面」— and it was DONE on 2026-09-04.
That is `docs/bugs/0639`, `backend/scripts/preserve-autocount-desc2-in-remark.mjs`
and `.github/workflows/preserve-autocount-desc2-in-remark.yml`, which park the
book's wording in `scm.mfg_sales_order_items.remark` under the label `账本原文: `.

**What I did wrong.** I read the importer, the schema and the render path, found
that `description2` is invisible on sofa/bedframe lines and is regenerated by the
item PATCH, and built a carry-into-remark tool with a NEW marker `AC原文: `. I
never searched the tree for an existing solution, so I did not find 0639 — which
names the same owner request, the same column, the same destination and the same
reasoning. **Reading the code that has the bug is not the same as checking
whether the bug is already fixed.**

**How it was caught, and what it would have cost.** The plan run against
production (read-only, run 34236801891, 2026-09-08 14:13Z) proposed 1,814
updates. Four sampled at random ALL looked like this:

```
before: 账本原文: Divan:8”+1”leg(12pcs)/Mgap:14”/Col:PC151-01
after : 账本原文: Divan:8”+1”leg(12pcs)/Mgap:14”/Col:PC151-01
        AC原文: Divan:8"+1"leg(12pcs)/Mgap:14"/Col:PC151-01
```

The text was already there. My "already quotes the text" guard did not fire
because the two copies differ only in TYPOGRAPHY — the live `description2` the
2026-09-04 run copied from carries the salesperson's smart quotes (`”`, `’`),
while the committed book snapshot carries straight ones (`"`, `'`) and flattens
the line's newline to a space. Byte comparison called them different strings.
Measured over all 1,814:

| | lines |
| --- | --- |
| already carry the existing `账本原文` label | **1,650** |
| of those, the same text once quotes/whitespace are normalised | 1,294 |
| no label at all — the genuine residual | **164** |

So applying it would have written a second, near-identical copy of the book's
words onto **1,650** lines. Nothing was applied; the plan path is read-only by
construction and the apply path was never dispatched.

**The residual IS real: 164 lines**, and they have one cause. Every one is a
line that did not exist, or was rewritten, AFTER the 2026-09-04 run:

| remark today | lines |
| --- | --- |
| `compartment corrected 2026-09-04` (sofa compartment lanes) | 140 |
| `topped up from AutoCount SO-… DtlKey …` (lines added later) | 17 |
| empty | 3 |
| `SAND/35”`, `MODENZA-05 (DARK OLIVE)` — **customer text, not our note** | 4 |

**Root cause of the residual, traced** — and it is a defect in 0639's own fix,
not in the lanes that created these rows. `decide()` in
`preserve-autocount-desc2-in-remark.mjs:160-166` reads `description2` first and
falls back to the book snapshot ONLY when `description2` is empty:

```js
if (current && !(gen && current === gen)) { text = current; origin = 'description2'; }
else if (current) return { action: 'skip', reason: 'description2 is already our generated summary' };
else { /* ... fall back to book.so.get(key) ... */ }
```

A line whose `description2` has ALREADY been replaced by our generated summary is
SKIPPED — never consulting the book, which still holds the original words in the
committed snapshot. That is precisely the state of a line rewritten by a later
lane. **The script skips exactly the lines that have already lost the text**, so
the residual regrows every time another lane touches these rows.

**Fix.** Not shipped in this PR, and deliberately so — see below. The fix is one
branch in `decide()`: when `description2` is empty **or** equal to the generated
summary, fall back to the book snapshot instead of skipping. Then re-run the
existing workflow. Note for whoever does it: 4 of the 164 carry what reads as
CUSTOMER text, not our machine note, so the owner's 2026-09-04 ruling
「如果是我们导入的就不需要」 does not cover them — `SHAPE=append` keeps both and
is non-destructive; `SHAPE=overwrite` would discard a customer's words.

**Why the fix is not in this PR.** This entry exists because a tool was built and
merged into a live cutover on the strength of reading rather than measuring. The
correct response is to remove the hazard first and land the root fix as its own
reviewed change, not to ship a second change in the same breath as the retraction.

**What this PR does.** Deletes `backend/scripts/backfill-so-desc2-into-remark.mjs` [gone],
`backend/scripts/lib/desc2-remark.mjs` [gone], `backend/tests/desc2IntoRemark.test.mjs` [gone]
and `.github/workflows/backfill-so-desc2-into-remark.yml` [gone]; rewrites this entry;
and corrects the `docs/modules/sales-order.md` section that described the
retracted `AC原文` scheme as if it were the system's behaviour.

**The one finding worth keeping** from the retracted work, because 0639 did not
record it: the invisibility is NOT uniform, measured by RUNNING
`buildVariantSummary` against the blobs `import-ac-outstanding-so.mjs` writes —
sofa returns `PC151-01 Sand`, bedframe `BF-01 Sand / DIVAN 8 + LEG 2 / GAP 12`,
and mattress/accessory returns `""`. So `description2` is hidden behind the
variant summary on sofa and bedframe lines and still VISIBLE on the rest — and
the PATCH's `|| null` means the first edit of a mattress line NULLS the book text
outright. The lines where the words were still visible are the lines where an
edit destroys them completely. 0639's "root fix still open" note covers this.
