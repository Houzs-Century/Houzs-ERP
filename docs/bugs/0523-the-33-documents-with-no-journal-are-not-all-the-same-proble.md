### 老板的指示

看过补帐选项之后，2026-08-23：**先只查清楚，不动帐。**

所以这支 probe 只量、不写，而且**分界才是它要交的东西**，不是总数。

### 为什么单号不能拿来分

单号的 YYMM 是**开单那个月**，不一定等于**单据的日期**。用单号去切，是拿标签当事实。
这支用的是单据自己的 `invoice_date`，分界线 **2026-08-18** —— PR #2427 上线那天。

### 一个可能解释掉整批的差别

**「没有 ACTIVE 分录」和「从来没有过分录」是两回事**，而自检分不出来 —— 它筛的是
`posted = true AND reversed = false`，所以**一张分录被冲销掉的单据，看起来跟从来没
过帐的一模一样**。

而冲销是正常的：取消单据本来就会冲销它的分录。

这支把两者分开。**如果七月那批大部分是冲销，那批根本没有问题。**

### 还查什么

分界线之前、从来没有分录的那批，逐一检查过帐函式**真正会拒绝的三个输入**：
`company_id` 是空的、日期是空的、金额 <= 0。

三个都是 0，就代表单据本身没毛病 —— 那是下一步要查的方向，不是这支能回答的。

另外从**帐本自己**读出停摆的区间（分界线前最后一笔、之后第一笔），而不是从部署纪录
推 —— 部署纪录只能告诉你程式码什么时候换，帐本才能告诉你影响什么时候开始。

### 公开纪录的限制

这个 repo 和它的 Actions log 是**公开**的，而这些是应付和应收。

所以只印**数量和分类**，不印单号、金额、客户或供应商。真正的数字在系统自己的
Self-check 画面 —— 那是私有的，也是老板该看的地方。公开的 log 能承载的是**形状**：
几张、落在哪一格、为什么。
