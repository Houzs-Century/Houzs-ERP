# Inventory & Costing Integrity — Risk Register (read-only audit)

**Date:** 2026-07-25
**Trigger:** Owner asked, beyond the known double-post class, "正常 ERP 还有没有什么可能导致我们的 Inventory 数据不对、Costing 不对的?" — a systematic enumeration of EVERY way inventory quantity or costing can go wrong in this ERP, ranked by risk, with code evidence, saying which are already guarded and what detection to add.
**Method:** Static trace of `origin/main` (worktree `chore/costing-integrity-audit`, cut from `b5f13fb6`). No production query was run; every claim cites `file:line`. Where a runtime SIZE is needed, this audit recommends (and for the one concrete new defect, ships) a read-only detector rather than asking the owner to run SQL (repo rule).
**Scope boundary:** Plain double-posting / idempotency is owned by a SEPARATE audit and is deliberately NOT re-analysed here. This register covers the OTHER classes. No costing/FIFO/document-post code was changed — investigation + docs + one read-only detector only.

## How costing works here (one paragraph, so the register reads)

Stock is bucketed by `(warehouse_id, product_code, variant_key[, batch_no])`. Every stock event is a row in `scm.inventory_movements`; an AFTER-INSERT trigger `trg_inventory_movement_fifo` (`backend/scripts/scm-schema/inventory-fifo-trigger.sql:267`) is the SOLE consumer: an `IN` opens an `inventory_lots` row at `unit_cost_sen`; an `OUT` consumes open lots oldest-first (`fn_consume_fifo` / `fn_consume_fifo_batch`, `ORDER BY received_at ASC, id ASC`, `FOR UPDATE`), writes `inventory_lot_consumptions` (the COGS ledger) and stamps `total_cost_sen` on the OUT. Two on-hand truths are derived independently: `scm.inventory_balances` = signed movement sum (`0084_multicompany_views.sql:180`) and `scm.v_inventory_value` = `Σ qty_remaining × unit_cost_sen` over open lots (`0106_report_views_company_id.sql:141`). They MUST agree; they can drift.

## RISK REGISTER — highest severity first

Legend: **Corrupts** = qty / cost / both. **Guard** = what already stops or detects it. Severity weighs money impact × likelihood × invisibility.

### R1 — [HIGH] `writeMovements` is best-effort: a document can post while its stock movement silently fails
- **Corrupts:** qty AND cost.
- **Evidence:** `writeMovements` catches every insert error and RETURNS `{ok:false}` instead of throwing — "a failed movement insert does NOT roll back the document post (audit-DLQ style)" (`backend/src/scm/lib/inventory-movements.ts:11,104-141`). Callers (GRN `postGrnAndRollup`, `deductInventoryForDo` at `delivery-orders-mfg.ts:925`, stock-take POST at `stock-takes.ts:741`, returns) log the failure but leave the document in its posted/shipped status. A GRN can read "received" with no lot; a DO "shipped" with no OUT and no COGS.
- **Guard / detection:** PARTIAL. Callers surface `movementErrors` in the response/audit note, but nothing reconciles document status against movement existence after the fact. The two shipped detectors (`check-inventory-integrity.mjs`, `check-uncosted-cogs.mjs`) reconcile the LEDGERS against each other, not the DOCUMENTS against the ledger — a GRN that posted with zero movements produces no lot and no OUT, so it is INVISIBLE to both (there is nothing to be inconsistent with).
- **Recommendation:** A read-only "posted-document vs movement" reconciliation: for each non-cancelled GRN/DO/DR/stock-transfer in a posted/shipped state, assert ≥1 `inventory_movements` row exists for `(source_doc_type, source_doc_id)`; list the orphans. SELECT-only, same workflow shape as the existing checks. (Do NOT make `writeMovements` throw without owner sign-off — the audit-DLQ posture is deliberate and changing it is a money-path change.) **Detector SHIPPED (this PR):** `backend/scripts/check-posted-doc-movements.mjs` + `.github/workflows/posted-doc-movements-check.yml` — covers GRN / DO / DR / STOCK_TRANSFER / STOCK_TAKE, groups orphans by doc type, annotates the legitimate zero-movement cases (zero-variance stock takes; service-only / zero-qty docs). SIZING only; changes no post/movement code.

### R2 — [HIGH] Foreign-currency GRN booked at rate 1 when the currency's master rate is unset — silent mis-cost, never re-healed by FX
- **Corrupts:** cost.
- **Evidence:** `safeRate` degrades a missing / non-positive / non-finite rate to **1** (`backend/src/scm/lib/fx.ts:47-50`), and a brand-new currency's `currencies.rate_to_myr` "defaults a new currency to 1 until the owner sets a real rate" (`fx.ts:62-84`). So a GRN in, say, RMB posted before the owner enters the RMB rate folds the raw foreign figure into the lot as if it were ringgit — `toMyrSen(x, 1) === x` (`fx.ts:57-59`). The guard is explicitly against ZEROING the money, not against a wrong-by-the-FX-factor cost. `recostFromGrn` re-reads the GRN's OWN stored `exchange_rate` (`recost.ts:248`), so if that stored rate was 1 at post time, the recost re-applies 1 — the error is sticky. The `recost.ts:236-241` comment names exactly this: "rate 1 means 'this price is already MYR', so a blip on an RMB GRN capitalises the raw RMB figure into the lot."
- **Guard / detection:** DETECTOR + WRITE-PATH GUARD. Zeroing was already prevented; the wrong-by-the-FX-factor 1:1 rate is now refused at the POST boundary (below), and the read-only detector sizes any legacy occurrences.
- **Recommendation:** A read-only check: GRNs / PIs whose `currency <> 'MYR'` but `exchange_rate = 1`, joined to lots they created — that pair is almost always an un-rated foreign receipt. Also worth a WRITE-path guard (owner-gated): refuse to POST a non-MYR GRN/PI whose currency has no positive master rate, rather than silently defaulting to 1. **Detector SHIPPED:** `backend/scripts/check-foreign-rate-one.mjs` + `.github/workflows/foreign-rate-one-check.yml` — GRNs joined to their own lots, PIs joined via `grn_id` to the lots their recost would fold, with the lot value at risk (treats a NULL rate as 1). SIZING only; changes no FX/costing code.
- **WRITE-PATH GUARD SHIPPED (DRAFT, staging-first):** `backend/src/scm/lib/fx-guard.ts` refuses a POST when the document currency is non-MYR AND no positive rate is available — the operator entered no positive rate on the doc AND the currency master's `rate_to_myr` is missing / non-positive / non-finite (the value `safeRate` would coerce to 1). Returns 422 `foreign_rate_unset` ("Set the &lt;CUR&gt; exchange rate before posting this &lt;doc&gt;"), never a 500. The block keys on the MASTER rate being unset, NOT on the effective rate being 1: a deliberately-entered operator rate of 1 posts; an unset master that defaults to 1 is refused. It reads the RAW master rate and does NOT touch `safeRate`/`toMyrSen`/`masterRateForCurrency` (the READ-path coercion is correct and relied on across FIFO). Wired at GRN `POST /`, GRN `/from-pos`, GRN `/from-po-items` (pre-validated over all buckets before any insert), and PI `POST /`; PI `/from-grn`, `/from-grn-items` inherit a rate already gated at GRN create. Unit-tested in `backend/src/scm/lib/fx-guard.test.ts` (20 cases). NOT proven against a real Postgres posting flow — staging validation remains. Ref #&lt;PR&gt;, `fix/r2-block-nonmyr-rate1`, owner 2026-07-25. Changes POST behaviour (a foreign doc with no set rate is now REJECTED instead of mis-costed — staff-visible).

### R3 — [HIGH] Positive stock ADJUSTMENT / STOCK-TAKE with no priced open lot creates a PERMANENT zero-cost (cost-less) lot — **NEW defect, detector shipped**
- **Corrupts:** cost (creates owned qty with RM0 basis → RM0 COGS when it sells).
- **Evidence:** The trigger's positive-ADJUSTMENT branch costs a new lot `v_unit_cost := COALESCE(NULLIF(NEW.unit_cost_sen,0), v_avg_cost, 0)` (`inventory-fifo-trigger.sql:212`) — the SKU's open-lot weighted average when the caller passes no cost, FLOORED at 0. Two callers hit that floor when the SKU has NO open lots to average: stock-take POST ALWAYS writes the variance ADJUSTMENT with `unit_cost_sen: 0` (`stock-takes.ts:727`), and a manual adjustment passes `unit_cost_sen` only if the operator typed one (`inventory-adjustments.ts:125` sends `Number(body.unitCostSen ?? 0)`). On a first-ever-stock or all-consumed SKU, `v_avg_cost` resolves 0 → the lot opens at 0. Unlike a GRN "Pending price" lot, `recostFromGrn` is keyed to `grn_items` only (`recost.ts:219`), so an ADJUSTMENT / STOCK_TAKE lot is NEVER re-costed — the RM0 basis is permanent and under-states COGS the moment FIFO reaches it.
- **Guard / detection:** Was NONE. **This audit ships a detector:** `backend/scripts/check-costless-stock.mjs` + `.github/workflows/costless-stock-check.yml` — open lots with `unit_cost_sen <= 0`, split into (1) PERMANENT (ADJUSTMENT / STOCK_TAKE — the defect), (2) PENDING (GRN — self-heals), (3) OTHER, each with a `refAvgCost` (the SKU's other priced open lots) as a candidate repair basis. SELECT-only, `workflow_dispatch`, own concurrency group, exit 0.
- **Recommendation:** Owner-gated fix (staging-first): force a cost on the write path — stock-take POST and a positive adjustment should carry the SKU's known avg cost (or require the operator to enter one) rather than 0 → the trigger fallback then never floors. Backfill the stranded lots at `refAvgCost` or an owner-supplied basis. Logged in `BUG-HISTORY.md`.

### R4 — [MEDIUM] Cancelled DO leaves its COGS consumptions attributed to the cancelled document (non-dropship path)
- **Corrupts:** cost/reporting (qty nets to 0 correctly; COGS ledger keeps a cancelled sale's consumption).
- **Evidence:** `reverseInventoryForDo` reverses a cancelled DO by writing a POSITIVE ADJUSTMENT (`qty = +net_out`, `unit_cost_sen = round(out_total_cost/out_qty)`) per plain bucket, or a batch-restoring IN for sofa buckets (`delivery-orders-mfg.ts:1435-1461`). It does NOT delete the original `inventory_lot_consumptions` rows the ship wrote — only the DROP-SHIP path does that, inside `fn_reverse_dropship_do_out` (`:1365-1372`). So for a NORMAL DO the signed movement balance returns to 0 and a fresh lot is added at the average consumed cost (at the BACK of the FIFO queue, not the original lot position), but `v_cogs_entries` / `inventory_lot_consumptions` still carry the cancelled DO's consumption. Any COGS report summed from consumptions counts a cancelled delivery; the re-added lot's basis is an average, not the original per-lot costs.
- **Guard / detection:** PARTIAL. Qty is correct (idempotent existence check at `:1335-1340`), value is approximately restored. The consumption-attribution and FIFO-reordering side effects are unguarded and undetected.
- **Recommendation:** Read-only check: `inventory_lot_consumptions` whose `source_doc_id` is a CANCELLED DO — sizes cancelled-sale COGS still in the stream. Owner decides whether the non-dropship cancel should also restore consumptions (mirror `fn_reverse_dropship_do_out`). **Detector SHIPPED (this PR):** `backend/scripts/check-cancelled-do-cogs.mjs` + `.github/workflows/cancelled-do-cogs-check.yml` — joins consumptions (`source_doc_type='DO'`) to CANCELLED DOs, split by `is_dropship`: non-dropship = the R4 size; dropship = an anomaly (the delete fn should have cleared them). SIZING only; changes no cancel/costing code.

### R5 — [MEDIUM] Landed-freight per-unit rounding: lot value can differ from the allocated charge by up to (qty/2) sen per line
- **Corrupts:** cost (small, bounded).
- **Evidence:** `allocateLandedCharges` distributes the freight pool so `Σ allocatedChargeCenti === chargePool` EXACTLY (last positive-qty line absorbs the remainder, `landed-allocation.ts:117-138`). But the lot stores a PER-UNIT cost: `perUnitCharge = Math.round(alloc / qty)`, `landedUnitCostMyr = base + perUnitCharge` (`:140-146`). Re-multiplying by qty (`qty × round(alloc/qty)`) does not equal `alloc` unless `qty | alloc` — so the freight actually carried in the lot value drifts from the allocated column by up to `qty/2` sen per goods line. The `Σ allocated === pool` invariant holds on the ALLOCATION column but not on the re-derived lot VALUE. `recost.ts:381-383` folds freight the same per-unit way, so the drift is consistent, not compounding.
- **Guard / detection:** The remainder-absorption guards the ALLOCATION total; nothing guards the per-unit re-multiplication. Impact is bounded and typically sub-ringgit per line.
- **Recommendation:** Accept as known rounding (document it), OR store the allocated charge on the lot as a total and derive per-unit only for display — a design change, low priority. No detector needed; magnitude is inherently small.

### R6 — [MEDIUM] Variant-key recomputed at 30+ write sites from a loose attribute bag — any alias miss re-buckets stock (the MAKOTO root class, generalised)
- **Corrupts:** qty AND cost (an OUT keyed differently from its lots consumes zero → uncosted OUT + qty drift; an IN keyed differently opens a parallel bucket).
- **Evidence:** `computeVariantKey(itemGroup, attrs)` is the single algorithm (`backend/src/scm/shared/variant-key.ts:103`) but it is CALLED at 30+ sites, each mapping its own line shape onto `VariantAttrs` (grep: `grns.ts:429,780,2158,2268,2550,2952`; `delivery-orders-mfg.ts:595,900,1197,1881,2569,2582,2702,3150,3713,3884,3927`; `delivery-returns.ts:349,451`; `consignment-notes.ts:293`; `consignment-returns.ts:295`; `inventory-adjustments.ts:79`; `so-stock-allocation.ts:288`; `recost.ts:363`; `sofa-batch-guard.ts:77`). The key folds MANY aliases for the same physical attribute (`fabricCode/colorCode/colourCode/fabricColor`, `seatHeight/depth`, `legHeight/sofaLegHeight`, `variant-key.ts:35-68`). If a write site passes the fabric under a field name the helper does not alias, or omits `item_group` so the per-group attribute list is empty, the SAME physical item yields a DIFFERENT key. The COEs already trace one instance of this (the resync DELTA OUT keying to a different `batch_no`/`variant_key` than the ship, `inventory-ledger-divergence-coe.md` §2). Historical rows are explicitly NOT migrated (`variant-key.ts:56-57`), so legacy POS sofas already sit under keys missing seat/leg.
- **Guard / detection:** The single-source helper + its alias set is the main guard; `sofa-batch-guard.ts` guards the sofa batch case. Divergence that slips through surfaces as the MAKOTO pattern, which `check-inventory-integrity.mjs` (#1254) DETECTS (qty drift + uncosted OUT) but does not attribute to a key mismatch.
- **Recommendation:** No new detector (the ledger detector already catches the SYMPTOM). Preventive: a shared mapper that every route uses to build `VariantAttrs` from a line (so the field-name mapping lives in ONE place, not 30), and a lint/test asserting IN and OUT of the same document produce identical keys. Design work, owner-gated.

### R7 — [MEDIUM] Negative adjustment / manual OUT is a check-then-act race and shorts silently on a lost race
- **Corrupts:** qty AND cost (a shorted OUT decrements the balance but consumes/costs less).
- **Evidence:** A negative manual adjustment reads available qty from `v_inventory_lots_open` (`inventory-adjustments.ts:82-97`) and THEN inserts the movement — not atomic. Two concurrent negatives can both pass the pre-check; the trigger's `fn_consume_fifo` takes `FOR UPDATE` (so it never double-consumes a lot or goes below zero, `inventory-fifo-trigger.sql:63-66`) but it DISCARDS `qty_short` (`:87,193-198`), so the loser's movement lands as a real `-qty` with less consumed → the exact discard-a-short divergence the COEs document, reached by a race instead of an oversell.
- **Guard / detection:** `FOR UPDATE` prevents lot corruption / negative lots (the serious failure). The residual is a shorted movement, which `check-inventory-integrity.mjs` query (2) DETECTS (Σ OUT qty ≠ Σ consumed). Likelihood is low (concurrent manual adjustments on one bucket).
- **Recommendation:** Covered by the existing detector; no new work. If the write path is ever hardened, persist `qty_short` so the short is self-evident (already the COEs' deferred item 3).

### R8 — [LOW] FIFO order is INSERT order, not physical receipt date — out-of-order data entry mis-layers lots
- **Corrupts:** cost basis (consumes the wrong layer first; qty unaffected).
- **Evidence:** The lot's `received_at` is set to `NEW.created_at` (`inventory-fifo-trigger.sql:168`), i.e. the movement's insert timestamp, NOT the document's real receive date. `fn_consume_fifo` orders `received_at ASC, id ASC` (`:62`). So a GRN entered LATE for goods that physically arrived EARLIER opens a lot at "now" — it goes to the BACK of the FIFO queue and is consumed last, even though it should be consumed first. A backdated receipt cannot insert AHEAD of already-open older lots. With uniform costs this is invisible; with rising/falling costs it books the wrong COGS layer.
- **Guard / detection:** Ties are deterministically broken by `id` (no ambiguity); `received_at` is never NULL (defaulted). But there is no way to honour a real-world receipt date that differs from entry order. Impact is only when unit costs move between layers.
- **Recommendation:** Accept and document, OR (owner-gated) let a GRN stamp `received_at` from the document's receive date so FIFO layers by physical arrival. Low priority. No detector (not an inconsistency, a policy choice).

### R9 — [LOW] `fn_consume_fifo` / `fn_consume_fifo_batch` do not filter `company_id`
- **Corrupts:** cost/qty ONLY IF a bucket spans companies (it does not today).
- **Evidence:** Both consumers match on `(warehouse_id, product_code, variant_key[, batch_no])` with NO `company_id` predicate (`inventory-fifo-trigger.sql:55-63,112-119`), unlike `fn_reconcile_uncosted_out` which pins company (`0154_scm_oversell_retrocost.sql:139`). In principle an OUT could consume another company's lot in the same warehouse+SKU bucket.
- **Guard / detection:** De-facto safe: warehouses belong to a single company and a lot inherits its movement's company (`inventory-fifo-trigger.sql:20-26`), so `warehouse_id` already isolates company. This only becomes real if a warehouse is ever shared across companies.
- **Recommendation:** Add `AND company_id = NEW.company_id` to both consumers when the FIFO layer is next touched (defence in depth); no detector needed while warehouses stay single-company.

## ALREADY GUARDED / RULED SAFE (the COE discipline — so the owner sees what is solid)

- **Concurrent OUTs double-consuming a lot — SAFE.** `fn_consume_fifo` / `fn_consume_fifo_batch` take `FOR UPDATE` row locks and `LEAST(qty_remaining, needed)` (`inventory-fifo-trigger.sql:63-66,121-124`); a second OUT waits and can never drive a lot below zero or double-consume. (The residual is a discarded short, R7 — a separate, detected condition.)
- **FIFO tie-break / NULL ordering — SAFE.** `ORDER BY received_at ASC, id ASC` with `received_at` never NULL (defaulted to the movement's `created_at`) and `id` as a deterministic tiebreaker (`:62`). No mis-ordering from ties or NULLs. (Entry-order-vs-physical-date is R8, a policy limit, not a bug.)
- **Freight allocation total — SAFE.** `Σ allocatedChargeCenti === chargePool` exactly, remainder absorbed by the last positive-qty line, with divide-by-zero and no-service-line no-op guards (`landed-allocation.ts:19-25,117-138`). (Only the per-UNIT re-multiplication drifts — R5, bounded.)
- **FX zeroing — SAFE.** A malformed / missing / non-positive rate degrades to 1, never 0, so a bad rate can never zero out money; MYR is always 1 (a byte-for-byte no-op) (`fx.ts:35-59`). (A genuinely-wrong 1:1 foreign rate is R2 — a different failure the guard does not cover.)
- **Purchase-return / stock-transfer cancel reversal — SAFE (once).** `reverseMovements` reverses by opposite-direction movement with a ledger-recomputed signed-net idempotency guard (a bucket already at net 0 is skipped), so calling it twice is a no-op and a partial reversal only reverses what's left (`inventory-movements.ts:316-459`). DO/DR are deliberately NOT routed through it (their partial UNIQUE indexes would reject the same-key opposite row) — they use signed-ADJUSTMENT reversals instead (`:330-336`).
- **Drop-ship DO cancel — SAFE.** `fn_reverse_dropship_do_out` restores + deletes the DO's lot consumptions (originals return at original cost), zeroes the OUT cost stamps, and writes a balance-only add-back, avoiding both the phantom-lot (cancel-before-receive) and the stranded-consumption (cancel-after-receive) faults (`delivery-orders-mfg.ts:1355-1389`). (Only the NON-dropship path leaves consumptions — R4.)
- **Oversell replenished by a NON-GRN IN never retro-costs — DOCUMENTED, detector shipped (#1231).** `fn_reconcile_uncosted_out` is wired only to GRN post; a stock-transfer / stock-take / adjustment / consignment-receive that replenishes an oversold SKU does not retro-cost the prior short. Root cause + `check-uncosted-cogs.mjs` in `docs/inventory-costing-oversell-coe.md`. Not re-reported here.
- **Movement ledger vs FIFO ledger divergence (the MAKOTO 3-vs-4) — DOCUMENTED, detector shipped (#1254).** `check-inventory-integrity.mjs` reconciles signed movement sum vs Σ lot qty AND Σ OUT qty vs Σ consumed. Root cause in `docs/inventory-ledger-divergence-coe.md`. Not re-reported here.
- **Inter-warehouse stock transfer atomicity — FIXED (#1241, audit R3).** Transfers are made atomic (`lib/stock-transfer-atomic.ts`). Not re-analysed.
- **PI / GR-price correction after shipment — HEALED by recost.** `recostFromGrn` re-derives the authoritative cost (PI > GR > Pending) and cascades lots → consumptions → OUT movements → DO → SI, conserving `Σ(qty × cost)` for lines that share a lot identity (`recost.ts:31-45,207-405`); invoked on GRN edit (`grns.ts:2361,2833`) and PI create/edit (`purchase-invoices.ts`, `recostForPi`). Foreign-rate edge is R2; the cascade itself is sound.
- **Service SKUs FIFO-exempt — CORRECT.** Only `SVC-*` lines are skipped from FIFO capture; accessories ARE costed (`docs/inventory-costing-oversell-coe.md` §4). Not a gap.
