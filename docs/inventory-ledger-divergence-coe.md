# Inventory Ledger Divergence — Movements vs FIFO Lots/COGS COE (Correction of Error)

**Date:** 2026-07-25
**Trigger:** Owner opened the Stock Breakdown drawer for SKU `MAKOTO RC(S)-FVI BRONZE` (2990 SOFA MAKOTO RELAX CHAIR), KL warehouse, and found the movement ledger and the FIFO ledger disagreeing on the same SKU: the MOVEMENTS list ends at running balance **3** (5 IN − 2 OUT), but the FIFO lots sum to **4** and COGS shows only **ONE** consumption. Two OUT movements were recorded on the SAME delivery order (`2990-DO-2607-018`, 23/07 11:47 and 12:22, 35 min apart) but only one lot-consumption exists.
**Status:** Root cause TRACED against the code (static trace of `origin/main`; no prod query needed to prove the mechanism). A READ-ONLY DETECTOR sized the exposure across all SKUs (PR below). **Go-forward engine fix now built as a DRAFT** (migration 0195 — the OUT-branch batch→plain-FIFO fallback) together with a **historical data-repair backfill** (`backfill-fifo-divergence.mjs`, DRY-RUN by default, staging-first, owner-run) — both DRAFT, STAGING-FIRST, NOT auto-merged; the historical repair is a separate, explicitly owner-triggered step. The specific MAKOTO symptom is also logged in `BUG-HISTORY.md` (HIGH).

## 1. Incident — what the owner saw

The Stock Breakdown drawer for MAKOTO RC(S)-FVI BRONZE (KL):

- **MOVEMENTS (4):** IN +3 (`2990-GRN-2607-010`, 13/07) → running 3; IN +2 (`2990-GRN-2607-017`, 20/07) → running 5; OUT −1 (`2990-DO-2607-018`, 23/07 11:47) → running 4; OUT −1 (`2990-DO-2607-018`, 23/07 12:22) → running 3.
- **COGS (1 consumption only):** 23/07 11:47, `2990-DO-2607-018`, −1, RM530, from lot `2990-GRN-2607-010`.
- **STOCK LOTS (owned):** 2 remaining from GRN-010 + 2 from GRN-017 = 4. **TOTAL QTY (OWNED) = 4.**

So the MOVEMENT ledger (`inventory_movements`, signed sum) says **3 on hand**; the FIFO ledger (`inventory_lots.qty_remaining`) says **4 on hand**; and the COGS ledger (`inventory_lot_consumptions`) has consumed **1**, not 2. Two OUT movements exist, one consumption. The two ledgers that must be one truth are off by exactly one unit — the second OUT decremented the running balance but consumed no lot and booked no COGS.

## 2. Root cause — traced against the code, not guessed

**The FIFO engine is per-row and correct; the fault is that the OUT branch SILENTLY DISCARDS a short, and a resync delta OUT can produce a FALSE short even when stock is on hand.**

**The write path (all cited, `origin/main`):**

- **The only consume path is the AFTER-INSERT trigger.** `writeMovements` does a plain `INSERT` into `inventory_movements` (`backend/src/scm/lib/inventory-movements.ts:116`); there is NO JS-side consumption. Every OUT's COGS is produced solely by `trg_inventory_movement_fifo` → `fn_inventory_movement_fifo` (`backend/scripts/scm-schema/inventory-fifo-trigger.sql:267`, AFTER INSERT FOR EACH ROW).
- **The OUT branch always consumes — and DISCARDS the shortfall.** The OUT branch calls `fn_consume_fifo` (plain) or `fn_consume_fifo_batch` (sofa/dye-lot) and then only persists `total_cost_sen = v_result.total_cost_sen` onto the movement (`inventory-fifo-trigger.sql:176-198`). The `qty_short` the consumer returns is **thrown away**. `fn_consume_fifo` matches lots on `(warehouse_id, product_code, variant_key, qty_remaining>0)` ORDER BY `received_at, id` (`:55-63`); `fn_consume_fifo_batch` ADDITIONALLY requires `batch_no = p_batch_no` **exactly** (`:118`). If the loop matches ZERO lots, its body never runs: `v_remaining` stays = qty, it returns `total_cost_sen = 0`, `qty_short = qty`, inserts NO `inventory_lot_consumptions` row, and decrements NO lot. Result: the OUT movement is a real row (the signed balance decrements) but the FIFO ledger is untouched — a permanent movement-vs-lot divergence of exactly the shorted qty, with COGS missing for those units.
- **The first ship is idempotent, so the second OUT is NOT a re-post of it.** `deductInventoryForDo` guard #1: if ANY OUT movement already exists for the DO, it no-ops (`backend/src/scm/routes/delivery-orders-mfg.ts:834-841`). The first-ship path physically cannot write a second OUT.
- **The second OUT comes from the delta-resync path.** The only other path that writes a DO OUT is `resyncInventoryForDo` (`delivery-orders-mfg.ts:1141`), invoked when a SHIPPED DO's lines change (qty increased / line added). It computes `delta = target_qty − current_net_out` per bucket and, when `delta > 0`, writes a fresh DELTA OUT of `delta` units (`:1256-1269`) — deliberately a new INSERT so the AFTER-INSERT trigger fires (`:1131-1136`). The MAKOTO second OUT at 12:22, 35 min after the 11:47 first ship, is exactly this: the DO was edited to ship one more unit, and the resync wrote the +1 OUT.

**The mechanism, put together.** The resync DELTA OUT at 12:22 went through the trigger, whose consumer matched **zero open lots** for that OUT's consume key — so `fn_consume_fifo`/`fn_consume_fifo_batch` returned the whole unit as `qty_short`, the OUT branch discarded it, and the movement landed with `total_cost_sen = 0`, no consumption, no lot decrement. Because 4 units (GRN-010 = 2, GRN-017 = 2) were physically on hand at 12:22, this was a **FALSE short**: stock existed that a matching consume would have eaten. MAKOTO is a **SOFA**, so its OUTs route through `fn_consume_fifo_batch` (exact `batch_no` match); the most likely trigger for the zero-lot match is that the resync delta OUT's resolved `batch_no` (or `variant_key`) did not equal the open lots' — the "sofa/bedframe legacy POS-vs-Backend key + batch" fragility already flagged as a separate noted risk in `docs/inventory-costing-oversell-coe.md` §4. The first OUT matched (it consumed GRN-010 for RM530); the resync-time key resolution diverged for the second.

**Tool that proved it:** static trace of `origin/main` — `writeMovements` is the sole insert path (`inventory-movements.ts:116`) and the trigger is the sole consumer (`inventory-fifo-trigger.sql:267`); the OUT branch discards `qty_short` (`:193-198`); `deductInventoryForDo`'s guard #1 rules out a first-ship double-post (`delivery-orders-mfg.ts:841`); `resyncInventoryForDo` is the only other DO-OUT writer (`:1256-1269`). The runtime SIZE of the exposure (how many SKUs, how many RM) is measured by the detector shipped in §3 — production numbers land when the owner runs it.

## 4. What the audit RULED OUT

- **The second OUT is a duplicate re-post of the first ship — FALSE.** `deductInventoryForDo` guard #1 (`delivery-orders-mfg.ts:834-841`) no-ops when ANY OUT already exists for the DO. The first-ship path cannot write twice; the second OUT came from the delta-resync path (`resyncInventoryForDo`), i.e. the DO was edited after shipping.
- **The FIFO trigger swallowed a runtime ERROR — FALSE.** `fn_inventory_movement_fifo` has no `EXCEPTION` block; an error inside the AFTER-INSERT trigger would RAISE and roll back the movement INSERT, so the OUT row would NOT exist. The OUT row DOES exist and the first OUT (same DO) costed correctly — so the trigger was active and ran to completion. It consumed nothing by DESIGN (matched no lots), it did not error.
- **A concurrency race where the lots were momentarily 0 at 12:22 — FALSE.** The lots are present NOW (4 units; 2 of them GRN-010, which predates the DO), and `fn_consume_fifo` takes `FOR UPDATE` row locks; there was physical stock on hand at 12:22. A key-matching consume WOULD have found it. This is a consume-KEY mismatch (sofa batch / variant), not an availability race.
- **A genuine oversell (ship more than on hand) — NOT the trigger here.** On-hand was 4 and only 1 more unit was shipped, so the second OUT was not short of physical stock. It is the SAME discard mechanism the oversell COE documents (`fn_consume_fifo` returns `qty_short`, the OUT branch discards it) but reached by a FALSE short from a key mismatch, not by insufficient inventory.
- **A manual / legacy movement insert bypassing the trigger — LOW.** `writeMovements` is the single insert path and always fires the trigger; there is no trigger-disabled insert in the DO code, and the first OUT on the same DO costed correctly, proving the trigger was live for this SKU.
- **`restampDoActualCost` zeroed the cost — NOT the cause.** It only READS OUT/IN movements and copies their cost onto the DO lines (`delivery-orders-mfg.ts:529+`); it never writes movements, lots, or consumptions. It faithfully reflects the missing cost downstream — it does not create the ledger divergence.

## 6. Lessons

- **Two ledgers that must be one truth need a check that they agree.** `inventory_movements` (the running balance) and `inventory_lots`/`inventory_lot_consumptions` (the FIFO owned qty + COGS) are derived from the same events but by different mechanisms — the app's own on-hand views already sum them separately (`inventory_balances` vs the lot rollup). Nothing was reconciling the two until a human noticed a 3-vs-4 in a drawer. A read-only reconciliation is the cheapest possible guardrail for a money-critical invariant.
- **Discarding a shortfall hides a divergence forever.** The OUT branch throwing away `qty_short` is the same fault the oversell COE found — an OUT that consumes less than it ships leaves no trace on the movement it lives on. "Best-effort, will be reconciled later" only holds if the shortfall is RECORDED; a discarded short is invisible until the ledgers are cross-joined.
- **A FALSE short is worse than a real one.** The oversell COE's short was a real stock shortage awaiting replenishment. This one shorted against stock that was PHYSICALLY PRESENT because the consume key (sofa batch / variant) did not match — so it will NEVER self-heal, no replenishment is coming, the stock is already there. Key resolution on the resync path must match the key the first ship used, or every edit-after-ship risks a phantom uncosted OUT.
- **Size before fixing money data.** The safe first move on a money-critical divergence is a read-only detector (this PR), not a hot fix — it quantifies the exposure and hands the owner the numbers, with zero risk to the FIFO layer.
- **Verify against the pipeline, not the symptom.** "Two OUT, one COGS" looked like a duplicate movement; tracing the code showed the first-ship path is idempotent and the second OUT is a legitimate resync delta whose consume matched no lot — so the fix is in key resolution + shortfall handling, not in de-duplicating movements. The ruled-out list (§4) is what stops the next person chasing the phantom-duplicate theory.
