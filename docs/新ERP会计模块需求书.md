# 新 ERP 会计模块需求书

> **这份文件怎么用**
> 把整份丢给新 project 的 Claude Code，第一句话跟它说：
> 「这是需求书。**先读完，讲你的理解给我听，不要写任何代码。** 特别注意第 6 节的边界规则 —— 这个 repo 有别人在同时开发。」
> 理解没问题之后，再叫它做第 5 节的阶段 0 和阶段 1，做完停下来给你看。
> 这份文件的内容来自三套已经在跑的 ERP 的实战经验 —— 哪些做对了、哪些踩了坑、哪些当初该第一天就定案却后来才补（补的时候全系统十几处跟着改）。

## 1. 背景

| | 系统 1（Venture Portal） | 系统 2（Hookka ERP） | 系统 3 |
|---|---|---|---|
| 定位 | 集团内部／控股，公司之间互开单 | 制造＋零售，完整进销存 | 进销存，会计科目表刚重做 |
| 成熟度 | 中 | **最高，底子最扎实** | 低，会计链路多处断掉 |
| 最强的地方 | 部门维度、内部分摊、付款单 void 冲得干净 | 单一过账门、期初机制、控制科目自动对账 | 会计科目表 UI、付款单过账 |
| 最大的洞 | 没有「先记账后付款」的供应商账单 | （已修得差不多） | **收款不入账、采购发票不入账** |

三套系统各自独立踩坑，最后得出的结论高度一致 —— 那些一致的结论，就是下面第 2 节的铁律。

### 新系统的定位（重要，会影响取舍）

**Trading（纯买卖，不生产）＋ B2C 为主**，业务形态最接近系统 3。所以：

**可以砍掉的**
- 制造成本、BOM、物料分摊、月末在制品 —— 系统 2 的「材料成本引擎试了三版」那整块不用做
- 成本 ＝ 进货价 ＋ 运费分摊，系统 3 的收货单这块已经做对了
- 长账期赊销的比重下降（但不是不做，B2B 客户还是有）

**必须加重的**
- **收款方式多、笔数多、金额小**：现金、刷卡（多家收单行）、线上转账、分期
- **对账是主干功能，不是附加功能**（见 3.5 节）—— 刷卡的钱是收单行扣掉手续费、隔几天才把净额汇进银行，中间这段必须有账挂着
- 电子发票的 **B2C 合并发票**规则跟 B2B 逐张开不一样

## 2. 铁律：第一天就要定案的 12 件事

这一节最重要。三套系统的共同教训是：**这些东西后来补，代价是全系统改十几处。**

### 2.1 全系统只能有「一个过账引擎」

所有单据（销售发票、采购发票、收款、付款、CN/DN、折旧、存货、工资）都必须调用**同一份**记总账的功能。不准各写各的。

- 系统 1：规则散在应用程式、数据库 trigger、数据库函数三个地方，互相打架，把发票错标成已付清
- 系统 3：三个建单入口各抄一份，其中一份抄漏了没人发现 —— 画面显示「已记账」，实际上没记
- 系统 2 的结论：过账只留一道门，无论谁、从哪条路建单，都走同一道门，不可能漏

**要求**：一张「什么动作 → 记什么分录」的规则表，看一眼就知道全部逻辑。每新增一种会自动记账的单据，**强制写一个自动化测试**（系统 3 出事的根本原因就是这块完全没有测试）。

### 2.2 状态用算的，不要用存的

「已付清 / 部分收款 / 未付」不要存成一个栏位，每次现场算「收够了没有」。

- 系统 1：部分收款收了 6 千，发票被标成全付清（存的状态跟实际对不上）
- 系统 3：总账的应收余额只会涨不会跌，完全不能看

### 2.3 不准有余额快取

银行余额、科目余额、报表数字一律现场从总账算。

- 系统 1：银行余额有快取和总账两套，漂移过好几次，靠人工纪律撑着 → 结论是直接废掉
- 系统 2：报表缓存「改了不刷新」，要靠版本号强刷

### 2.4 控制科目 = 明细加总，自动对账，第一天就装

应收（300-0000）、应付（400-0000）这类控制科目：

- 由系统自动维护，**禁止手工过账进去**
- 系统随时能自算「控制科目余额 vs 所有单据明细加总」，差多少、差在哪一张单，直接点名
- 系统 2 原话：这条是后来才装的，一装上历史问题全现形 —— **早装早发现**

### 2.5 单据日期驱动一切报表

报表按「单据日期」算，不是按「你按按钮那天」。旧单补录会自动回到它该在的月份。
系统 2 是后来改造的，波及十几处。

### 2.6 期初机制第一天设计好

旧系统带过来的欠款要有正式的「期初单」：进账龄、进客户欠款，但**不重复进总账**（总账走一条开账分录），两边天生对平。

系统 2 最痛的一次：期初没进来那阵子，收款被冲到账外单上，应收对账差了 6 万，一家客户逐张对了两天。
**规矩：先把期初对完，才开放收款。**

### 2.7 金额一律存整数（以「仙」为单位）

不用小数，永远不会有小数漂移。—— 系统 2

### 2.8 单据生命周期共用一套规则

建立 / 编辑 / 作废 / 冲销，全部单据共用同一套：

- **改单原号原地改**：号不变，自动冲掉旧账、记新账，改过几次都查得到（系统 2）
- **作废要冲整个家族**（含所有编辑痕迹），不是只冲最原始那笔 —— 系统 2 是踩过坑才进化成这样
- 作废用「藏起来」不用删，账本只加不改
- 系统 1 的付款单 void 做得很好：账、部门余额、银行余额全部原路退回

### 2.9 科目表结构与过账限制

- 科目：代码 ＋ 名称 ＋ 类型（资产／负债／权益／收入／费用）＋ 现金流分类 ＋ 父子层级 ＋ 可停用
- 编号沿用 AutoCount 式的「三位数-四位数」（300-0000）—— 系统 2、3 都是这套，会计同事熟悉
- 改名要留别名记录，旧报表照样认得（系统 2）
- **父层科目（底下有子科目的）不准过账，而且要真的拦下来** —— 系统 3 现在只是画面上显示一个「Header」标签，根本没拦，一笔真钱可以被记到「营业费用」这个大类本身
- 特殊科目标记：保留盈余、本年盈余、汇兑损益、凑整差额、默认银行／现金

### 2.10 权限与审批要写在代码里，不是写在文件里

系统 3 的现况：**任何登入的员工都能自己开一张付款单、自己一个人直接过账**，没有第二个人确认。「finance 负责付款审批」这句话只写在角色说明里，代码从来没检查过。记账的 API 也是任何人都能呼叫。

**要求**：过账、审批、作废这三个动作一定要检查身份；付款单要有金额门槛的审批（超过 X 元要主管批）。

### 2.11 数据库栏位命名第一天统一

系统 2 原话：底层的「列名转换层」是**最大暗坑，没有之一** —— 同一类 bug 复发过 4 次，每次症状都是卡上数字对不上；还有一次数据库约束漏了「部分付款」状态，部分付款整整坏了两周，只报「出错了」，最后靠加错误留痕才抓到。

### 2.12 单号生成要并发安全

系统 1 的付款单按张数编号，两个人同时按理论上会撞号（目前单人操作没事，人一多就会出事）。

### 2.13 「给人选的名字」和「代码里认的代码」必须是同一套

系统 3 的对账在找「PBB」「GHL」这几个死字，但开单画面的付款方式下拉选单后来改成协调员可以自己编辑，目前预设写的是「**Public**」，而且**根本没有 GHL 这个选项**。两边靠巧合对上，一改就断，断了还没有任何提示 —— 客户刷 Public Bank 的钱会永远卡在「未对上」。

**要求**：收款方式／收单行是一张**正式主档**（代码 ＋ 显示名称），画面上选的和对账认的是同一笔资料。真要分开，中间必须有翻译对照表，不能靠文字长得一样。

### 2.14 失败要吵，不要安静失败

系统 3：GHL／PBB／HLB 三家的报表如果误传 PDF，程式看不懂，但**不报错，安静解析出 0 笔**，人还以为传成功了。（同一个系统里，银行对账单那边就有好好挡下来并说明不支援 —— 两套做法。）

**要求**：任何解析、导入、过账动作，失败一律明确报错并说明原因，绝不允许「安静地什么都没做」。

## 3. 功能清单

标注 `[1]`／`[2]`／`[3]` = 这个做法参考哪个系统。

### 3.1 开单／发票

**流程**
- 销售：销售订单 SO → 送货单 DO → 销售发票 SI `[2][3]`
- 采购：采购单 PO → 收货单 GRN → 采购发票 PI `[2][3]`
- 库存在**送货／收货**时才真正加减，不是下单时 `[3]`

**开票方式**
- 从 DO 转开票，可以挑品项、挑数量**分批开**，系统自己记住还剩多少没开，开完为止不会重复开 `[2][3]`
- 手工新建
- 复制上个月的发票改一改再开 `[1]`
- 一键批量生成（例：固定的房租水电按人头分摊给各公司，一次生成全部草稿）`[1]`

**状态**
- 草稿（不入账）→ **发出那一刻才入账** → 部分收款 → 已收清
- ⚠️ 系统 3 的教训：不要把「直接建立」设成预设主按钮，草稿反而要额外选 —— 单据一按就生效，出错没有回头路

**科目怎么带**
- **按货品类别／料组自动带出收入和采购科目，开单的人不用选** `[2]` —— 比系统 1「每行自己选」更不会错，比系统 3「写死单一科目」更灵活；映射表要能在设定里改
- 保留手工指定的能力，给内部分摊这类特殊单用 `[1]`

**税**
- 税率在设定里设一次；**开单那一刻就把税算好、定死存在单上** `[2]` —— 之后就算改税率，旧单的作废／重记也用它自己当时的税，新旧永远对得上
- 关联公司互开的内部单据，税率 0% `[1]`

**B2C 专属**
- 零售单允许「一步成单」（现场交货、当场收款），不用硬走 SO → DO → SI 三步 —— 但**入账必须走同一个过账引擎**，不能因为流程短就另开一条捷径。系统 2 早期的「建单即发出」捷径，害采购侧 91 张里 90 张没进总账
- 顾客资料可非必填（散客），但要能当场补 TIN／公司资料（电子发票用）
- 电子发票分流：B2C 散客走**月度合并提交**，单笔超过 RM10,000 必须开个别的 —— 系统要自动判断走哪条
- 退货／换货流程要顺，B2C 的退货频率比 B2B 高很多

**其他**
- PDF 打印、批量打印、月底对账单
- 单价明细要能自我验证（例：底价＋各项加价加起来必须等于卖价才显示明细）`[2]`
- 价格由价格表自动带，改价要 admin 权限＋留记录（改多少、为什么、谁批的）`[3]`

### 3.2 应收

- 收款页选客户 → **自动列出未收发票（旧的排前面）** → 每张填收多少或勾全额 → 过账 `[2]`
- 支援：全额收 / 部分收 / 多张合并收一笔 / netting 互相抵消（不过银行）`[1]`
- **每笔收款必须记：收款方式 ＋ 收单行 ＋ 交易编号／批次号 ＋ 收款日期**（从收款方式主档选，见 2.13）—— 这几个栏位是后面所有对账的钥匙，缺一个就对不起来
- **刷卡收款不直接进银行科目**，先进「在途结算款」（见 3.5）
- **预收款**：客户先给钱、单还没开 → 挂在客户名下（用预收款科目），之后开票再冲掉；冲的时候只对子账，**不重复入账** `[2]`
- 收据可原号编辑、可作废、可打印
- **Debtor Aging**：按逾期天数分桶（当期／30／60／90＋），部分收款按余额算，收清的自动消失；未冲的预收款以负数列出；可导出；部门经理只看得到自己部门的 `[1][2]`
- 期初单：进账龄、进客户欠款，不重复进总账 `[2]`
- CN／DN 要做**完整**（批准后自动冲销应收和收入）—— 系统 1 做了半成品：能开能批，但批了只改状态不入账，到今天一张都没开过。**要么做完整，要么不要做**
- **到期日必填**；空白的到期日要视为逾期，不能当成正常 —— 系统 3 现在一张十年没收到钱的单，只要到期日空着，账龄报表永远显示「正常」
- **坏账认列流程** —— 系统 3 完全没有，收不回来只能整张发票作废，会把收入也一起冲掉
- 到期／逾期提醒（至少 dashboard 红字）`[1] 明列为缺口`

### 3.3 应付

**这块是系统 1 最大的洞，一定要补：**

- **供应商账单登记（PI）**：从 PO → GRN → PI 一条链，数量互相锁着，不会多收多付 `[2]`；也可手工建或扫描导入
- 「今天收到发票、下个月才付」中间这段**必须有地方挂着** —— 系统 1 完全没有，等于没有应付账龄
- **应付账龄 ＋ 到期提醒**
- **付款单（PV）**：
  - 逐行写：哪个户口出钱、记什么费用科目、多少钱
  - 可选要冲抵哪几张 PI
  - **审批流：草稿 → 送审 → 批准 → 过账**（系统 1 有，系统 3 完全没有）
  - **「批准」和「付款」要分开** —— 系统 1 是批准即付款，没有「批了、约好周五付」这个状态
  - 过账那一刻：记总账 **＋** 同步把被冲抵的 PI「已付金额」扣下去，两边一起动，不会各说各话 `[3] 这是系统 3 做得最好的功能`
  - 可贴附件（单据拍照）`[1]`
  - **科目选择要限制成「只能选真的可以过账的科目」** `[3] 教训`
- 支援：预付款、供应商 CN／折扣逐张抵扣、外币（记账汇率 vs 付款汇率，汇差自动进汇兑科目）`[2]`
- **采购退货要自动冲抵应付** —— 系统 3 完全没连起来，只有一个人工填的备注栏
- 付款批次 ／ 银行转账文件导出（DuitNow / bulk payment）`[1] 建议`
- 可用余额视图：每家银行扣掉待批付款单后**真正能动的钱** `[1]`
- 完整 void：账、余额、银行全部原路退 `[1]`

### 3.4 总账／会计科目

- **完整复式记账**，借贷永远相等，试算表常年 0.00 `[1][2]`
- 借贷相等做两层检查：程式一层、数据库一层 `[3]`
- **手工 JV 要有前端入口** —— 系统 3 后端做好了、画面上没有按钮，这种「做一半」最容易让人搞混。要有模板、可冲销、整张反冲
- **月份锁账**：锁了的月份，所有模块都不准动它的账 `[1]`
- **部门维度**：
  - 部门标签挂在**每一行分录**上，不是挂在整张凭证上 —— 系统 1 挂在整张上，跨部门的一笔业务得拆成好几张凭证
  - 部门是总账的正式维度，**不要做成第二本平行账本** —— 系统 1 的「部门 pool」是平行账本，要靠桥接才对得上，内部分摊会造成两边差异。新系统里部门页面应该只是一张报表
- **报表**：试算表、资产负债表、P&L（月度矩阵／报表式／分部门／分产品线）、现金流量表（含月度）、总账查询（按科目／按客户／按供应商）、财务仪表板
  - **每张报表出生就自带「与总账对平」的自检数字** `[2]` —— 后来补的话，补上之后每次出问题都能当场定位，所以第一天就装
  - 报表口径要统一：不要有的读发票、有的读总账（系统 2 后来把 P&L 采购段统一改读总账才顺）
  - 库存原则：你没上传盘点，库存就是 0 —— 报表上任何数都必须是自己给的数，一眼可验 `[2]`
- **审计日志**：谁动过什么、动之前长什么样 `[1][2]`
- 年结、固定资产折旧、月末存货过账、银行对账／Cash Book、工资过账（一键把薪水＋EPF／SOCSO／EIS 过进账，可撤销重来）`[1][2]`

### 3.5 对账（四层，新系统的主干）

先讲一个系统 3 没做、但**非做不可**的账务结构：

#### 「在途结算款」科目

B2C 刷卡的钱不是当场进银行的。顾客今天刷 1,000 → 收单行扣掉手续费 → 过几天把 985 净额汇进你的银行户口。中间这几天，钱在收单行手上。

```
顾客刷卡当下：    借 在途结算款 1,000     贷 应收／收入 1,000
收单行汇款进来：  借 银行          985     贷 在途结算款 1,000
                  借 手续费(费用)   15
```

**对账 ＝ 把「在途结算款」这个科目清干净的过程。** 清不掉的余额，就是还没到账或对不上的钱，一眼看得出来，还能自动套用控制科目自检。

系统 3 现在**整个对账功能一行账都不记**（当初讲好「这期先做对不对得上，记账留下一期」，那个下一期到今天没开始）。后果有三个：
- 刷卡手续费从来没进过账 → **P&L 的利润是虚高的**
- 银行余额跟系统永远对不上（系统记毛额，银行进净额）
- 对账只能「看到差异」，差异永远不会被消化掉

**新系统的规矩：对账确认的那一刻就产生分录，不留「下一期再说」。**

#### 四层，由内往外做

**第 1 层：控制科目 vs 明细自检**（阶段 0／1，最优先）
- 应收控制、应付控制、在途结算款，随时能自算「科目余额 vs 明细加总」
- 差多少、差在哪一张单，直接点名到单号 `[2]`
- 这层不装，后面三层对出来的差额永远解释不完

**第 2 层：日结／收银对账**（阶段 2，跟收款一起做）
- 每天收档：现金、各家收单行、线上转账，分别列「系统记录 vs 实点／实收」
- 现金要能记「实点金额」，差额进**长短款**科目，不是硬盖过去
- 当天不结，隔天就查不出是哪一笔 —— B2C 最容易失血的地方

**第 3 层：收单行结算对账**（阶段 2 尾）

系统 3 这块的骨架是对的，直接沿用，但要修掉几个洞。

*沿用（系统 3 做对的）：*
- 上传报表 → 自动比对系统里的收款 → 结果分四堆：**已配对／需要确认／没配对上／已忽略**（底层可记更细的状态，画面只给四堆）
- 「需要确认」点开列出候选，显示线索（金额一样／编号一样），可勾一笔或**好几笔**（一笔刷卡对应两张订单的情况）
- 系统自动配对的那堆，有「全部确认」一次搞定
- 两个常驻观察名单：**未到账收款**（系统记了、报表找不到）、**未对上的结算**（报表有钱、系统找不到单）
- 「没配对上」「手续费」两份清单可导出 Excel
- 权限：前后端各检查一次

*必须修的：*
- **各家收单行的差异做成设定档，不要写死在代码里**：文件格式（CSV／PDF）、有没有唯一交易编号、手续费怎么抓（报表直接给／总额减净额／从汇总区块按比例分摊）
- **没有唯一编号的收单行**（系统 3 的 GHL 就是）：明确标示「只能靠金额＋日期猜」，这类一律进「需要确认」，不允许自动确认
- **日期容差写在设定里** —— 系统 3 的设计文件写 3 天、代码实际写 7 天
- 误传格式要报错，不准安静解析出 0 笔（见 2.14）
- 收单行代码统一走主档（见 2.13）
- **配对确认 → 立刻产生分录**（清在途结算款、记手续费）

**第 4 层：银行对账**（阶段 4）
- **一开始就支援多个银行户口** —— 系统 3 写死只认一个 Hong Leong 户口，画面上根本没地方选别的
- **每加一家收单行，同一时间把「银行备注怎么认出这是哪家的钱」的规则一起补上**，不要分两次做 —— 系统 3 有 4 家收单行、只写了 2 条规则，另外 2 家的钱永远显示「应收但没收到」
- **沿用系统 3 的关卡设计**（这个做得很对）：这段期间的收单行报表还有「需要确认／没配对上」没清完，银行对账就挡住不给看数字，逼你先清干净
- 「应收 vs 实收 vs 差额」总表 ＋ 逐笔存款配对 ＋ 点开一笔存款看得到里面包含哪几笔刷卡
- ⚠️ 命名坑：「HLB 卡机（收单行）」和「Hong Leong 银行户口」是两回事，系统 3 要靠画面文字提醒人别搞混。新系统在**主档层面**就把「收单行」和「银行户口」分成两种资料，代码不共用同一个名字

---

**手续费的税**：刷卡手续费一般是含 SST 的服务，新系统要能把它拆成「费用 ＋ 进项税」，不要像系统 3 那样只当成一个给人看的数字。

### 3.6 每日看板（Daily Bank）

形态参考系统 1，但**去掉部门维度**，换成 trading ＋ 多收单行的场景。

**它要回答的一句话**：今天钱在哪里、真正还能动多少。

**版面（由上往下读）**
```
昨天结余
＋ 今天收到的钱（绿色，逐笔：收据号 ＋ 付款人 ＋ 收款方式）
＋ 在途结算款（刷卡了、收单行还没汇进来的，按收单行分列）
－ 等批／待付的付款单（橙色，逐笔：收款人 ＋ 单号 ＋ 描述）
＝ 可用余额（绿底）
```
最底一行：**所有银行户口加总的「真正能动的钱」**

**分列方式**：每个银行户口一块；在途结算款按收单行分（GHL／PBB／MBB／HLB…）

**必备操作**
- 日期随便翻：‹ › 逐天、日历直接跳、Today 一键回今天
- **Get image 一键复制成图片** —— 直接贴 WhatsApp 给老板。系统 1 的经验是这个小功能最常用
- PNG／PDF 导出

**口径规则（照系统 1 定的）**
- 「等批」只算已提交等审批的付款单，草稿不算
- 已经付掉的钱不再列出来（已经在余额里扣了），页脚要写清楚
- 余额**按总账实时算，不准用快取**（铁律 2.3）—— 所以跟试算表、对账页永远一致

**系统 1 点出的缺陷，新系统要修**：它靠时间戳倒推「某一天有哪些单在等批」，跨日的单会差一两笔。新系统要给每张付款单存一份正式的**状态变化历史**，任何一天都能精确还原。

### 3.7 报表清单

**共同规则**
- **打开就是最新的，不存在「跑报表」这回事** —— 每次从总账现场算（铁律 2.3）
- 所有报表读同一本总账，所以互相必然对得上。**两张报表数字不同 = bug，不是口径问题**
- 科目搜索：打「300-0000」或「salary」直接高亮跳过去
- 可导出 Excel／PDF
- ⚠️ PDF 导出用英文 —— 系统 1 的经验：PDF 引擎不支持中文，会变乱码

**清单**

| 报表 | 用途 |
|---|---|
| Trial Balance 试算表 | **体检表，永远必须 0.00**，不是零就是有 bug |
| P&L 损益表 ＋ Monthly P&L | 12 个月横排对比，科目可一层层展开（大类 → 小类 → 明细） |
| Balance Sheet 资产负债表 | |
| Cash Flow ＋ Monthly Cash Flow | 按科目预设的分类（经营／投资／融资）自动归类 |
| General Ledger 总账查询 | 逐科目逐笔查，每笔点进去看整张凭证 |
| Debtor Aging 应收账龄 | 30／60／90 天桶，部分收款按余额算，收清自动消失 |
| Creditor Aging 应付账龄 | 同上 |
| **在途结算款账龄** | 刷卡多久还没到账，按收单行分（新增，系统 1 没有） |
| 对账报告 | 银行月末数 ± 未清项 ＝ 账上数 |
| 日结报表 | 当天现金／各收单行／转账 vs 实收（见 3.5 第 2 层） |

**月结快照（阶段 4 一起做）**

系统 1 自己列的缺口：报表永远是活的。锁账挡得住新增，但**一旦解锁改了历史账，之前给老板的报表数字就跟着变了，而且没人知道变过**。

新系统：每月关账时把整套报表**定格存档**。以后随时能调出「当时给的那个版本」，也能比对「当时 vs 现在差在哪」。

**预算 vs 实际、今年 vs 去年**：排阶段 5。纯管理用途，不影响账的正确性，而且要先累积几个月实际数字才有东西可比。

## 5. 建议实现顺序

**每个阶段做完停下来验收，再往下做。不要一次全做。**

**阶段 0：地基**（第 2 节全部 12 条）
科目表结构、单据日期、金额单位、命名规范、生命周期规则、过账引擎骨架、权限模型、测试框架。
👉 这阶段没有画面可看，但省下来的返工最多。

**阶段 1：能自己平的账本**
科目表 UI（增／改／停用／拖拉层级）＋ 手工 JV ＋ 试算表 ＋ 总账查询 ＋ **控制科目自检（对账第 1 层）**。
验收标准：手工开几笔 JV，试算表是 0.00，控制科目自检通过。

**阶段 2：开单 ＋ 应收 ＋ 收款对账**（这阶段最大，可以再切两半）
零售一步成单／SO → DO → SI，草稿／发出／作废，收款（现金／刷卡／转账／分期，全额／部分／合并／预收），**在途结算款**，**日结（第 2 层）**，**收单行结算对账（第 3 层）**，Debtor Aging。
验收标准：刷一笔卡 → 上传收单行报表 → 配对确认 → 手续费自动进账 → 在途结算款清零。开单、收款、部分收款、作废四个动作跑完，总账和账龄两边对得上。
另外做：**每日看板（3.6）** —— 收款做好之后顺手就能做，老板每天要看。

**阶段 3：应付**
PO → GRN → PI 登记，Creditor Aging，付款单（审批 → 批准 → 过账），采购退货冲抵。
验收标准：一张 PI 分两次付清，账龄归零、总账对平、void 后全部原路退。

**阶段 4：报表 ＋ 银行对账 ＋ 期初 ＋ 锁账**
P&L、BS、现金流、月度矩阵、期初机制、月份锁账、审计日志、**银行对账（第 4 层，多户口）**、**月结快照（定格存档）**。
验收标准：每张报表的自检数字对上总账；银行户口余额 ＝ 总账银行科目余额；关账后能调出定格版本。

**阶段 5：加值功能**
SST／MyInvois、坏账、催收提醒、外币汇差、固定资产、年结、工资过账、付款批次导出、**预算 vs 实际 ／ 今年 vs 去年**。

## 6. 边界规则（重要，一定要遵守）

**这个 repo 有其他人在同时开发，销售、库存等模块已经在正式运作。**
你（Claude Code）只负责财务／会计模块。改坏别人的东西，代价很大。

### 6.1 可以做的

- 新增**财务模块自己的**档案和资料夹
- 新增资料表，但**表名一律以 `acc_` 开头**（例如 `acc_journal_entry`、`acc_chart_of_account`），一眼就看得出是财务的
- 在别人的模块里加**呼叫记账引擎的那一行**（见 7.3）

### 6.2 不可以做的

- ❌ 不准改别人现有资料表的结构（不准加栏位、改栏位、改型态）
- ❌ 不准改别人模块里的既有逻辑（销售怎么开单、库存怎么扣，都不是你的事）
- ❌ 不准改共用的设定档、路由、数据库连线设定，除非先问过人
- ❌ 不准重构、整理、优化别人的代码 —— 就算你看到写得不好，也不要动
- ❌ 不准删除任何现有档案

### 6.3 唯一允许碰别人模块的情况

财务模块要记账，需要别人在动作完成时通知一声。允许在这些地方**各加一行呼叫**：

```
销售模块：单据发出时      → 呼叫 记账引擎(这张单)
收货模块：收货确认时      → 呼叫 记账引擎(这张单)
收款模块：收款过账时      → 呼叫 记账引擎(这笔收款)
付款模块：付款单过账时    → 呼叫 记账引擎(这张付款单)
```

规则：
- **只加这一行，同一个档案里其他内容一个字都不准动**
- 记什么科目、借贷怎么走、怎么冲销，全部写在财务模块里面，别人不需要知道
- 加了之后要在交付说明里**逐一列出**：改了哪个档案、第几行、加了什么

### 6.4 动手前的程序

1. **先列清单**：打算新增哪些档案、要碰别人哪几个档案，列出来给人看过才动手
2. **开自己的分支**做，不要直接推 main
3. 做完交付时附一份清单：新增了什么、碰了别人哪几行

### 6.5 遇到冲突怎么办

如果你发现「不改别人的东西就做不下去」（例如某个资料表少一个栏位），**停下来问，不要自己决定**。列出：
- 为什么非改不可
- 打算怎么改
- 会影响到谁

## 7. 要老板决定的事（决定了才开工）

### 决定 1：SST ＋ 电子发票（MyInvois）要不要做？

三套系统里只有系统 2 接了 MyInvois，系统 1、3 完全没有税功能。

马来西亚的现况（2026-08 时点，建议再跟税务代理确认）：
- 年营业额 RM1M–5M 属第四阶段，2026-01-01 起已在强制范围内，但**宽限期延长到 2027-12-31**，2028-01-01 全面执法
- 年营业额 RM1M 以下豁免，**但如果是 RM1M 以上公司的子公司或关联公司，2026-07-01 起就要遵守** —— 系统 1 是集团内部互开单，这条很可能直接适用
- 2026-01-01 起，单笔超过 RM10,000 必须开个别电子发票，不能合并

👉 **建议**：税的**资料结构**（税率设定、税额栏位、税科目）阶段 2 就先放进去，成本很低；MyInvois 的实际对接可以排阶段 5。**千万不要像系统 1、3 那样连栏位都没有** —— 后补要动全系统。

B2C 还要多想一层：零售散客走**月度合并提交**，但单笔超过 RM10,000 要开个别的，所以顾客主档要留 TIN 栏位、开单画面要能当场补买家资料。系统 2 已经接过 MyInvois，实作细节可以直接参考它那边。

### 决定 2：分店／门市维度 —— ❌ 已拍板：不做

不做部门／门市维度。分录不带部门标签，报表不分部门看。

📌 给 Claude Code 的提醒：需求书里凡是提到「部门」的地方（参考自系统 1）一律忽略，**但底下那两条教训仍然适用**，将来万一要加维度时才不会重做：
- 若日后要加，标签挂在**每一行分录**上，不是整张凭证
- 若日后要加，做成总账的正式维度，**绝对不要做成第二本平行账本** —— 系统 1 的「部门钱包」就是平行账本，报表要靠一层折算才对得平，是它自己列为「重做一定要改掉」的第一条

### 决定 2b：每日看板（Daily Bank）—— ✅ 已拍板：要做

见 3.6 节。

### 决定 3：新 ERP 是给一家公司，还是多家／关联公司互开单？

多家的话，阶段 0 要多定案：公司之间的往来科目、内部分摊、合并抵消。
系统 1 就是这种场景，它的一键分摊和内部单据可以直接参考。

### 决定 4：要接哪几家收单行？（对账用）

系统 3 现在有 GHL、Public Bank、Maybank、Hong Leong 卡机四家，但只有三家有真实资料在跑（GHL 一笔都没有）。

新系统开工前要先列一张表：**哪几家、各家报表格式、有没有唯一交易编号、手续费怎么算、钱进哪个银行户口**。
这张表就是对账第 3、4 层的设定档，阶段 2 开工前要填好 —— 系统 3 正是因为分次补，才会有两家的钱永远对不上。
