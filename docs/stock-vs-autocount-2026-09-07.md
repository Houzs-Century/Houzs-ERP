## 白话文：一句话结论

**我们的库存跟 AutoCount，一共比了 996 个「货品 × 仓库」格子，789 个完全一样，
202 个对不上。**

**这 202 个里面，真正是我们导入时候导错的，只有 4 个格子、4 件货。**
其余 198 个都是同一个原因：**AutoCount 这九天还在继续出货收货，我们的系统从
8 月 29 日之后就没再接过它的账。** 我们的数不是算错，是旧了。

这两件事的处理方法完全相反 —— 一个要盘点，一个只要把这九天的单补进来 —— 所以
不能混在一起讲。

### 没有算进去的部分（这是刻意的，两边一起排除）

- **沙发**：AutoCount 一张沙发算一件，我们按 compartment（1A、CNR、L 位）分开算，

  121 件。**沙发要另外对，不能放在这张表里。**
- **服务类**（运费、丢弃、仓储）：AutoCount 把它们当有库存的货品管，我们当服务，
  服务不带库存。AutoCount 排除 -4,187 件，我们排除 16 个格子 / -4,149 件。
- 找不到对应货品或对应仓库的：**0**。**所有货品和所有仓库都对上了**，没有货
  掉在外面。

## 二、Stock Status（AutoCount 的 Remark2 对我们的备货状态）

比了 **2,882 张**已经跟 AutoCount 单号挂上的单。**2,499 张一致，383 张不一致。**
（一致的里面有 19 张只是字的先后顺序不同，例如 `ACC/BEDFRAME` 对
`BEDFRAME/ACC`，意思一样，算一致。）

### 不一致的四个原因

| 原因 | 张数 | 白话 | 例子 |
|---|---|---|---|
| 两边都写了，但写得不一样 | 191 | 对哪几类货齐了有分歧 | SO-013160：AutoCount 写 `READY`，我们写 `PARTIAL` |
| AutoCount 走在前面 | 111 | AutoCount 写了齐货，我们系统里找不到货可以配 | SO-012107：AutoCount `READY`，我们空白 |
| 我们这边没有 proceed | 76 | 单还没按「proceed」，系统一律当没货，跟仓库有没有货无关 | SO-011160：AutoCount `ACC`，我们空白 |
| 我们走在前面 | 5 | 我们配到货了，没人回头去 AutoCount 打字 | SO-000013：AutoCount 空白，我们 `BEDFRAME` |

### 对不上的组合，最常见的前十

| 张数 | AutoCount 写 | 我们写 |
|---|---|---|
| 83 | `READY` | （空白） |
| 46 | `ACC` | （空白） |
| 43 | `READY` | `BEDFRAME` |
| 35 | `READY` | `ACC` |
| 28 | `READY` | `PARTIAL` |
| 25 | `READY (PARTIAL)` | （空白） |
| 24 | `READY` | `BEDFRAME/ACC` |
| 21 | `READY (PARTIAL)` | `BEDFRAME` |
| 12 | `MATTRESS` | （空白） |
| 10 | `READY` | `MATTRESS/ACC` |

**一个方向性的事实：383 张里面有 300 张以上是 AutoCount 说「齐了」而我们说「没齐
或只齐一部分」。** 这跟上面库存那一节是同一件事的两个面 —— 货在 AutoCount 的账上
已经收进来了，我们的账还没收到，所以配不出货，状态自然写不出来。**先把库存补上，
这里大部分会自己好。**

`(空白) => (空白)` 有 2,339 张 —— 这些是两边都没写状态的单，一致，不用管。

## 三、这次修好的两个报错（都在对标工具本身）

**这两个错不会改到任何库存数字，它们改的是「为什么不一样」的答案。**
第一次跑（34132704988）给出的原因分类是错的，如果照着做，方向会完全相反。

### 1. 拿货品名字当证据，说是「已知的重复出货」

工具把 **14 个格子 / 139 件**归到「SO-2606-019 重复出货，已经查过了，等老板决定」，
其中包括整张表最大的一笔（`NTYR-CS LTX PIL @ BALAKONG`，+57）。可是同一次跑，
上面两行就写着：那两张重复的 DO 单，在我们系统里 **一个格子都碰不到**。

原因：判断式是「这个格子有那两张 DO 的记录 **或者** 货品名字开头是
KETTA/NTYR/TRION/XAMMAR」。重新导入之后那两张 DO 的记录没了，就只剩「名字开头」
在判断 —— 而 NTYR 是一整个枕头系列。**重复出货的意思是同一张 DO 出了两次；
一个格子连一张 DO 记录都没有，不可能重复出货。** 现在改成：那两张单还在，名字
这条才算数；单不在，就按记录实际显示的原因报。详见 `docs/bugs/0668`。

### 2. 「基准线」被人重新导出，等于没有基准线

工具靠「导入当天 AutoCount 是多少」来分辨两件事：**是我们导错了**，还是
**我们只是旧了**。这条基准线本来读 `ac-stock-balance.json.gz`。

问题是这个档不是基准线，是一个工作用的导出档，`export-ac-reimport.py` 每跑一轮
就重写一次 —— 光是 2026-09-07 这一天就被重写了三次，最后一次在导入之后。
**量过：重写之后的这个「基准线」跟今晚的现场数据，一个格子都不差，完全相同。**

于是「AutoCount 动过」这个原因永远命中 0 个格子，所有本来该归这一类的，全部滑到
下一个分类 ——「导入时就差了」，意思刚好相反。第二次跑（34133023365）就是这样报的：
**175 个格子 / 1,211 件「导入时就差了」**。

修法：另开一个**冻结的**基准线档 `ac-seed-baseline-balance.json.gz`，内容是
2026-08-28 23:27 那次导出，以后不再重写。修好之后（34133528726）同一个生产库、
同一份 AutoCount 快照，数字变成 **157 + 41 + 4**，真正导错的只有 **4 件**。
详见 `docs/bugs/0669`。

**这一条要记住：** 一个报告说「某个原因 0 笔」，跟「这个原因根本没在跑」，
在纸面上长得一模一样。

## 四、还不确定的（UNKNOWN，不要当成已知）

1. **冻结基准线比实际导入时间早约 22 小时。** 基准线是 2026-08-28 23:27，而我们
   系统里 `AC_CUTOVER` 的最后一笔写在 **2026-08-29 21:55**。8 月 29 日那一天
   AutoCount 的动作，会被算成「AutoCount 动过」，实际上可能已经导进来了。
   **偏差只有一个方向**：会把「我们落后」这一类算多一点点，把「导入时就差了」
   算少一点点。影响面小，但没有量过。
2. **177 个格子没有成本资料**，所以 RM 19,666.98 是**下限**，不是全部。
3. **那两张重复出货的 DO 单（DO-2607-005 / DO-2607-017）现在查不到记录**，这只
   证明记录不在了 —— **不代表当初那件事已经处理好。** 这仍然是老板要决定的一件事。
4. AutoCount 有一张 DO 的日期写到 **2026-09-19**（未来日期）。看起来是打单打错，
   没有去追。

## 怎么自己再跑一次

```
Actions → Stock vs AutoCount reconcile (read-only) → Run workflow
  target = prod
```

AutoCount 那一半是快照，因为 GitHub 的机器连不到公司内网。快照过期的话先重新导：

```
AC_CRED_FILE=<放密码的档案路径> python backend/scripts/export-ac-live.py
```

只读，只有 SELECT，不写不改，也不碰 `FurtherDescription`（那一栏整批扫会把
AutoCount 拖死）。今晚这一次跑了 1.4 秒。

**`ac-seed-baseline-balance.json.gz` 不要重新导**，除非库存真的重新导入了一次 ——
它一被重写，上面第 3 节第 2 条那个错就会原样再来一次。
