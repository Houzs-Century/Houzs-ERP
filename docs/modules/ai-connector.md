# AI Connector (MCP)

Staff ask Claude / ChatGPT / any remote-MCP app about the ERP with their OWN login. Read-only, except two confirm-first actions (book a meeting, send an email) that an admin must switch on.

## Address
- Connector URL: `https://erp.houzscentury.com/api/mcp` (2990: `https://erp.2990shome.com/api/mcp`).
- Discovery: `/.well-known/oauth-protected-resource` and `/.well-known/oauth-authorization-server` at the site root (Pages functions forward them to the Worker with `X-Forwarded-Host`; the Worker believes only company hosts — `routes/mcp.ts publicOrigin`).

## Rules
- Read-only by construction: a tool call re-enters the app in-process as a GET. `middleware/auth.ts` accepts an `hzmcp_` token ONLY with the per-isolate `x-houzs-mcp-inner` header and ONLY for GET/HEAD; a token used directly against `/api/*` gets 403.
- The one write door (`services/mcp-inner.ts admitMcpWrite`): a non-GET passes only with the inner secret AND `x-houzs-mcp-action` naming an action `confirm_action` armed a moment ago in this isolate, for this same token (single use, 30 s), AND method + the exact path it was armed for, which must match `ACTION_ALLOWLIST` for that action's kind: `POST /api/meetings/meetings` (meeting), `POST /api/mail-center/compose` (email), `POST /api/mail-center/threads/:id/reply` (mail_reply), `POST /api/assr/:id/notes` (note). Nothing else — orders, payments, stock adjustments, prices, payroll, approvals, deletes — is reachable. Test: `middleware/auth.mcp-write.test.ts`.
- Actions are confirm-first: `propose_meeting` / `propose_email` check the request like the form would (attendees and room against `/api/meetings/bootstrap`; From against `/api/mail-center/compose/senders`, the same rule as Compose), store it in `mcp_pending_actions` (10 min) and return a summary + `confirmationId`. `confirm_action` claims the row once (`UPDATE … WHERE used_at IS NULL AND expires_at > now RETURNING`, same token + person) and calls the ERP's own route as the person, so the route's own permission, mailbox rule and audit apply. Switches: System > AI Connector "Allow AI actions" (`app_settings.mcp_actions_enabled`, absent = OFF) covers meeting / email and is the master for all; the round-4b actions also need their own switch (`mcp_action_mail_reply_enabled`, `mcp_action_note_enabled`, absent = OFF), re-checked at confirm. Cap: 30 confirmed per person per 24 h. Logged in `mcp_calls` as kind + short line (recipients and subject, never the email body), and a successful confirm writes `audit_events` `ai_connector.action.<kind>` (actor = the person) on top of the route's own record (Mail Center outbound message, case timeline note).
- Own permissions: the inner call runs as the real user (`getUserById`), so every route's own permission, page access and company scope decide. `erp_get` takes `company` (HOUZS / 2990).
- Never readable: sign-in, TOTP, PIN, private mail, sync, public portals, the connector itself (`services/mcp-access.ts MCP_BLOCKED_PREFIXES`). Credential-shaped fields are stripped from every reply.
- Money fields by the ERP's own cohorts (`services/mcp-access.ts redactMoney`): margin / profit / any cost key only for `isFinanceViewer`; product / line unit cost also for `isProductCostViewer` (Purchasing). Unknown caller → all stripped. Added after the 2026-11-25 leak check found unitCostSen / costPriceSen / contractor_cost / fin_total_cost / cost_notes reaching a Sales Executive through the ERP's replies.
- Who may connect: holders of `ai_connector.manage` (Owner via `*`) always; everyone else after approval (`mcp_access`). Staff request on System > AI Connector; admins get a bell notice.
- Tokens: access 24 h, refresh 90 d (rotating), SHA-256 hashes only (`mcp_tokens`). Remove / Disconnect revokes at once.
- Every lookup is logged (`mcp_calls`) and shown on the AI Connector page.

## Tools
- Quick answers first (one call, a summary of a few thousand characters): `sales_summary` reads the Sales Report's Sales Order stage (`/api/scm/reports/fair-report?stage=so`) for the window and the same days one period earlier, plus top models and the trend from `/api/scm/sales-analysis`; `delivery_summary` reads `/api/scm/logistic-overview` the same way. Both take `period` (YYYY-MM / YYYY-Qn / YYYY, ending today at the latest) or `from`/`to`, and `company`. Only the window's own read must succeed; the comparison and the Sales Analysis are extras.
- `search` / `fetch` are the pair ChatGPT requires: `search` wraps `/api/search` into `{results:[{id,title,url}]}` with id `<hit type>:<id>`; `fetch` opens the record at its detail endpoint (`services/mcp-quick.ts FETCH_KINDS`). A receipt or product hit has no single record to open; its link is the answer.
- Every read (quick answers, search, fetch, `erp_get`) goes through `readValue` in `routes/mcp.ts`: the in-process GET as the person, then the credential strip. No quick answer runs its own SQL.
- `erp_get` takes `fields` (keep only those keys, any depth); replies are cut at `MAX_RESULT_CHARS` (30,000).
- `document_flow` finds the document (search, or a `type:id`), reads `/api/scm/document-flow/:type/:id` (the Relationship Map) and adds date and amount (RM) from each document's own detail read for the first 15 nodes — all through `readValue`, so money is stripped by cohort. Houzs has no job cards / production stage; the chain is SO → DO → invoice → payment and SO → PO → GRN → purchase invoice, plus returns and consignment.
- `get_pdf`: a Sales Order, Purchase Order, Sales Invoice or GRN comes back as the finished PDF file. The Worker draws it with the ERP page's OWN generator (`shared/src/vendor/scm/lib/sales-order-pdf-render.ts` / `purchase-order-pdf-render.ts` / `sales-invoice-pdf-render.ts` / `grn-pdf-render.ts`, the root `shared/` module both apps bundle; the Worker reaches it only through `backend/src/lib/shared-pdf.ts`), from the data the browser's print chain reads (`print-bundle.ts`): every read goes through `readValue` as the person, so their permission, company scope and money strip apply, and an unreadable payments ledger means no document. Stored in R2 `mcp-exports/<random key>.pdf` for 15 minutes, served by `GET /api/mcp/export/:key` as a download. Same Noto Sans SC subsets (fetched from the site's `/fonts/*.ttf`) and the same "refuse a glyph it cannot print" rule. What the Worker does differently (no canvas): JPEG / PNG photos and logos embedded as they are, WebP / GIF photos left out (a WebP `.thumb` falls back to the original first), PO sofa artwork drawn as schematics. A render failure falls back to the page link with the reason. A service case (customer copy, `/api/assr-print`) and a project debrief (`/api/projects-print`, finance cohort only — it carries cost and profit) are printed by the server as HTML: `mcp-exports/<key>.html`, sandboxed CSP. Delivery orders still answer with the ERP page link: their QR is a public `/d/<token>` scan link minted by the print-time read, which the AI must not mint. Purchase invoices, credit notes, returns and vouchers also answer with the page link. Houzs has no quotation document. The person's own read of the document must succeed first.
- Shared layout rules: the SO / PO layout and what it reads live in root `shared/` (frontend keeps one-line re-exports at the old `frontend/src` paths), because `backend/src` and `frontend/src` may not import each other (`scripts/check-layout.mjs`). They must stay DOM-free (the backend typecheck has no DOM lib); CI `changes` and both deploy filters treat `shared/**` as both halves; `tests/pdfSharedBoundary.test.ts` holds the graph inside `shared/` and pins the workflows and the three backend vitest configs. The layout reads its letterhead from a module-level host (`pdf-host.ts`), so the Worker renders one document at a time per isolate (`services/mcp-pdf.ts exclusive`).
- Round 3 (`services/mcp-round3.ts`, shaping in `mcp-quick2.ts`, `mcp-brief.ts`, `mcp-faq.ts`): `outlet_sales` (fair-report SO stage, month to date, split today / MTD per `venue`), `pos_sales` (booth POS: `/api/pos-admin/events` + `/report` per on-going / this-month event, at most 5; needs `pos.manage`; there is no separate 2990 POS endpoint, the booth POS is per company), `after_sales_summary` (`/api/assr/summary` + open cases `/api/assr?exclude_stage=completed,voided`, oldest first, up to 600 for ages), `attendance_today` (`/api/hr/attendance?date=today`, HR only; note that GET also closes forgotten punches, as the page does).
- Round 4 (`services/mcp-round4.ts`, shaping `mcp-round4-shape.ts`, periods `mcp-period.ts`; tests `mcp-round4.test.ts`): `stock_check {query}`, `inventory_summary`, `uninvoiced_deliveries {min_age_days}`, `po_awaiting_receipt`, `customer_overview {query}`, `after_sales_sla`, `service_cases {period}`, `company_report {period}`; `outlet_sales` / `pos_sales` now take `period`. Period tools take `period` = today | week | month | last_month | quarter | year | custom (+ `from`, `to`) or YYYY-MM / YYYY-Qn / YYYY, and compare with the same days of the previous period and the same dates last month (`resolvePeriod`). `pos_sales` reads at most 3 events, each once for the window and once over the comparison days (split by `by_day`). `company_report` = six reads: the finance dashboard (P&L by month; `scm.payment_voucher.post`), the Sales Report SO stage now and before, AR and AP aging, the service-case summary; a section the person may not read is null plus a `notAvailable` line, and a P&L key `redactMoney` removed stays absent, never 0.
- `daily_brief` (+ prompt `daily-brief`): six reads at once: `/api/badge-counts` (approval counts + `mail-waiting` — a COUNT only; Mail Center itself stays blocked), `/api/scm/mfg-sales-orders/mine` (customer delivery date past or within 3 days), `/api/scm/mfg-purchase-orders?status=outstanding` (supplier date), `/api/assr/my-cases`, `/api/attendance/leave` (pending, approvers), `/api/announcements/banner` (not acknowledged). A 403 becomes a line in `notAvailable`; the rest still answers.
- `export_excel {list, search, status, from, to, fields}`: lists in `EXPORT_LISTS` (sales orders, DOs, sales invoices, POs, GRNs, service cases, suppliers, customers), paged as the person 4 pages at a time, cap 5,000 rows (`truncated`). Hand-built .xlsx (`services/mcp-xlsx.ts`: zip + XML, deflate via CompressionStream, no library): header row, widths, nested objects one level (`supplier.name`), arrays dropped, `*_sen` / `*Sen` columns as RM. Stored in R2 `mcp-exports/<key>.xlsx` for 15 minutes, served by `GET /api/mcp/xlsx/:key` (attachment). Logged in `mcp_calls` with the row count.
- Limits (`services/mcp-ratelimit.ts`): 30 `tools/call` a minute and 600 a day per person, counted from `mcp_calls` (index `mcp_calls_user_idx`); a refused call is logged with note `rate limited` and not counted again; the answer is an `isError` tool result, never a 500. initialize / tools/list / prompts never count; the leak check reads through `readEndpoint`, not `callTool`, so it is never limited. Shown read-only on the admin page.
- Answer cache: quick answers and `daily_brief` keep a successful answer 30 s (heavy summaries 60 s) per isolate, keyed by person + company + tool + arguments (`(cached)` in the log target). A permission change takes effect within 60 s.
- `prompts/list` + `prompts/get` offer four ready-made questions (`PROMPTS`) plus one per role (`services/mcp-round4c.ts ROLE_PROMPTS`: owner_morning_report, finance_review, purchasing_review, outlet_manager_review, after_sales_review, hr_today; each names its tools; listed only when one of its tools is).
- Round 4b actions (`services/mcp-write-actions.ts`, tests `mcp-round4bc.test.ts` + `middleware/auth.mcp-write.test.ts`): `propose_mail_reply {thread_id | thread_search, body, reply_all, to, cc}` reads the thread as the person (`GET /api/mail-center/threads/:id`, which marks it read for them, as opening it does; the mailbox scope decides) and fixes the recipients (last sender; reply_all adds the others minus our own mailboxes) and `afterMessageId` (the route's 409 if a colleague replied since), so what the summary shows is what is sent. `propose_note {id, note, category}` takes a case number or `assr_case:<id>`, reads the case as the person, and posts to `POST /api/assr/:id/notes` (`service_cases.write | create | manage` + case scope). Sales orders, purchase orders and customers have no note / comment endpoint, so they take no notes. There is no PO approval step in this ERP (a PO goes DRAFT → confirm; amendment approval changes qty / prices and cancel approval cancels), so there is no PO-approval action.
- Role-aware `tools/list` (`mcp-round4c.ts TOOL_GATES`): a tool is hidden when the person passes none of its endpoints' ERP gates, written as the ERP's own predicates (`scmAreaReadable`, `fairReportAccess`, the routes' flat keys); action tools are hidden while their switch is off. Hiding never grants: a hidden tool called directly still runs through the ERP and answers "no access" / "switched off". `company_report` stays listed for anyone who can read one of its sources (the Sales Report, accounting or service cases), because the ERP lets them read that section.
- Structured output: every quick answer has a loose `outputSchema` (no required keys) and returns its JSON as `structuredContent` beside the text (`withStructured`, applied after the cache). Heavy summaries (`company_report`, `outlet_sales`, `inventory_summary`, `after_sales_sla`) are cached 60 s, the rest 30 s, keyed by person + company + tool + arguments.
- Consistency: outlet names are merged case-insensitively (`outletKey`, shown upper case, `spelledAs` lists the spellings) in `outlet_sales` and `company_report`; outlet rows link to the Sales Report (filtered to the outlet when it has one spelling, since that filter is exact); aging rows link to Accounting > AR / AP aging.

- `data_gaps` (round 4d, `services/mcp-data-gaps.ts`): four reads as the person: AP aging `unappliedSen` (supplier payments / advances / credit notes not knocked off a bill), the open SO tabs (no `customer_delivery_date`, 5 pages a tab), the SKU Master `/api/scm/mfg-products?anchorState=1` (no supplier cost = `costAnchorState` empty; no price = sell price, Price 1 and Price 2 all empty; no category; SERVICE items left out), `/api/scm/mfg-sales-orders/customers` (no phone). A section the person may not read is a `notAvailable` line.

## Help tools (no ERP data; `services/mcp-howto.ts`)
- `how_to {question?, topic?}`: ranks the guides (`mcp-howto-guides-*.ts`, index `docs/modules/how-to-guides.md`) by keyword / title (English + Chinese + Malay keywords; simple scoring, no AI call) and returns the top 1-3 full SOPs (purpose, prerequisites, who, fields, click-by-click steps whose links carry `?highlight=<button>`, checks, result, warnings, undo, approvals, deadlines, common mistakes, worked example, related, next step, contact). `canDo` = the page's own route guard evaluated with the ERP's predicates (`mcp-howto-types.ts gatePasses`: `scmAreaReadable`, `page_access`, flat permissions, capabilities); false adds the "ask your supervisor or admin" note. No match = the list of titles.
- `module_overview {module?}`, `glossary {term?}`, `explain_error {text}` (each entry's `match` is the backend's own message text), `onboarding {role}` (first week for outlet-sales, 2990s, purchasing, warehouse, finance, after-sales, admin). Prompts: `how_do_i`, `explain_module`, `what_does_it_mean`, `explain_this_error`, `my_first_week`.
- Screen map (`services/mcp-screen-map-*.ts`, types `mcp-screen-types.ts`): one entry per route in `frontend/src/App.tsx` (redirects excepted): title, purpose, sidebar path, sections, tabs and every button / menu / tab action with what it does, the permission it needs and its side effects; high-traffic pages in full detail. `explain_screen {path?, visible_text?}` finds the page from the URL, or from labels read off a screenshot (title 3, tab / section 2, button 1.5), and returns it with `canDo` per action (page guard from `mcp-route-guards.json`, plus the action's own gate). `where_is {thing}` ranks pages + their buttons (and boosts the page of the best how_to guide) and returns the sidebar path and a link with `?highlight=<button>`. Server instructions: a screenshot of the ERP -> read the URL bar and labels -> `explain_screen`. Prompts `explain_this_screen`, `where_is_it`. Honesty: `mcp-screen-honesty.test.ts` (every route covered, every label in `frontend/src`, each declared page gate equals its App.tsx guard).
- `?highlight=<label>` (`frontend/src/components/HighlightFromUrl.tsx`, matcher `lib/highlight-match.ts`, mounted once in `Layout`): finds the visible, laid-out element with that text / aria-label / title / placeholder (trimmed, case-insensitive; a span inside a button gives the button), retrying about 3 s while data loads; scrolls to it, pulses a gold outline for about 6 s (CSS animation, no timers) with a "Here" tip, then drops the parameter with `history.replaceState`. No parameter = nothing happens; it never clicks or edits. A button that exists only on desktop (e.g. "New Purchase Order") is not highlighted on the phone.
- `show_me {guide_id?, step?, path?, label?}` (`services/mcp-show-me.ts`, data `mcp-help-shots.ts` + `mcp-help-shots.json`): a screenshot of the real page with a red box and an arrow on the button. Returns the screenshot as an MCP `image` item (WebP; the Messages API does not take SVG images), a 15-minute link (`/api/mcp/export/<key>`, R2 `mcp-exports/<key>.html`) to the annotated SVG (screenshot + red box + arrow + caption), the real page link with `?highlight=`, the box coordinates, and the note "screenshot uses test data, layout is the same". `how_to` steps and `where_is` places that have a picture carry `showMe`. Pictures: `frontend/public/help-shots/*.webp` (served by Pages; the Worker fetches them from the public origin), boxes in the JSON. Captured by `npm run capture:help-shots` (`scripts/capture-help-shots.mjs`): local vite, every `/api` call answered inside the script with demo data, every other host blocked, a fake local token, desktop 1440 x 900, viewport WebP q45 at 1200 px; a page that does not render with the demo data is skipped. Stored in the repo, not R2 (no production upload from a laptop); `mcp-show-me.test.ts` keeps the total under 8 MB and fails with "re-capture screenshots" when a boxed label disappears from `frontend/src` or a picture is missing.
- Gap log: a help question nothing matches is logged in `mcp_calls` with note `no-guide` and the question with emails and long numbers removed (80 chars); System > AI Connector "Questions with no guide yet" lists them grouped, without names.
- Honesty: `mcp-howto-honesty.test.ts` fails when a guide's page is not a route in `frontend/src/App.tsx`, a quoted label / highlight / field label is not in `frontend/src`, or an error `match` is not in `backend/src`. A UI rename means fixing the guide in the same PR. Guides are English; Claude translates.

## Brief and alert emails (round 4d)
- Opt-in on System > AI Connector "Email me" (`pages/AiConnectorBrief.tsx`; `GET/PUT /api/mcp-admin/me/brief`, `POST /me/brief/test`). Only people with connector access (`hasMcpAccess`) can switch on; time = a quarter hour in MYT (default 08:00), weekdays or every day. Stored in `mcp_brief_subscriptions` (migration `20261127T0400_mcp_brief_alerts.sql`).
- Runs AS the person (`services/mcp-proactive-run.ts asPerson`): a short-lived token for client `mcpc_brief` (the leak check's pattern), checked by `mcpIdentity`, every read through `readAs` (the connector's in-process GET + credential and money strip), revoked when the run ends. No service account. `mcpc_brief` tokens are hidden from "My connected apps" and the connected count.
- Brief: cron `*/15` (`runBriefs`), `daily_brief` built as the person, Mondays (MYT) also `data_gaps` (a test brief from the button always carries it). Due at or after the person's time, at most 3 h late, once a day: `last_brief_day` is claimed (`UPDATE … WHERE last_brief_day <> today RETURNING`) BEFORE building, so a rerun never sends twice. At most 8 people / 120 s a run; the rest go next run.
- Alerts: cron `*/30` (`runAlerts`), opted-in people least recently checked first, at most 10 / 120 s a run. Newly overdue SO / PO (supplier or delivery date passed in the last 2 days) worth at least RM 5,000, service cases whose deadline passed in the last 24 h, stock below zero. Debounce: `mcp_alert_sent` (person + key + MYT day), a key is not emailed again for 7 days; SO / PO / case keys carry the date, so a revised date alerts again. All defaults in `services/mcp-proactive.ts ALERT_THRESHOLDS` / `BRIEF_SETTINGS`, shown read-only to admins.
- Sent with the ERP's sender (`services/email.ts sendEmail`, purposes `ai_brief` / `ai_alert`, switches `email.ai_brief` / `email.ai_alert`, absent = on). Each send is one `mcp_calls` row (`email:daily_brief` / `email:alerts`, counts only, never the body) plus the sender's own `email_log` row (subject, status). Note: the sender's outbox (`email_outbox`) keeps the HTML for retries, as for every ERP email.
- Unsubscribe: every email has a link `/api/mcp/brief/unsubscribe/<token>` (`routes/mcpBrief.ts`, public, mounted before `/api/mcp`) and `List-Unsubscribe` + `List-Unsubscribe-Post` headers (one click in Gmail / Outlook). GET shows one button so a mail scanner opening the link changes nothing; POST turns both emails off.
